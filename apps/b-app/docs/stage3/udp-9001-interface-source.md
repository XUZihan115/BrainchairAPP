> 本文档**以当前 Unity 工程里已经写好的代码为准**（`unity-wheelchair-sim/Assets/Scripts/WheelchairSim/`），
> 不是设计稿、不是任务书转述。整理时间：2026-10-21。

## 0. 先给结论（三条）

1. **端口是 9001，不是 9100**；指令回传是 9002。
2. **校验不是 CRC32**，是 **1 字节校验**，算法可自动识别（累加和 / 异或和 / CRC8），**推荐固定用累加和 Sum8**。
   帧里根本没有 4 字节校验位，所以 CRC32 这套塞不进来。
3. 帧格式是 **`AA 55 | 类型 | 长度 | 数据 | 校验 | 0D 0A`**，指令码 **0x01～0x06** 与你们看到的一致。
   但请注意：这跟工程里 TCP / 串口 / 蓝牙用的 `AA 55 | LEN | SEQ | CMD | ARG×2 | CRC8` **不是同一套帧**，别照那份写。

**Unity 端接收代码已经写完并在场景里默认开启**（`EnableWifiUdp = true`），
但**还没有和真实发送端做过联调**——代码路径完整，实测要等这次对接。

## 1. 网络参数

| 项目 | 值 | 说明 |
|---|---|---|
| 传输层 | UDP | 无连接，不保证到达、不保证顺序 |
| Unity 监听端口 | **9001** | `0.0.0.0:9001`，本机所有网卡 |
| Unity 回传状态端口 | **9002** | 发给"最后一次发指令的那台机器的 IP : 9002" |
| 状态帧频率 | **5 Hz**（200 ms） | 由后台线程发送，不受渲染帧率影响 |
| 字节序 | **小端（Little-Endian）** | 所有多字节整数 |
| 单帧最大数据区 | 60 字节 | 指令帧实际只用 1～2 字节 |
| 广播 | 支持 | Unity 端 `EnableBroadcast = true`，对端可发广播地址 |

> 如果 B 端不方便在 9002 监听：把 Unity 侧 `Wifi Status Port` 设为 `0`，状态帧会回到"对端发指令用的源端口"。
> 如果 B 端坚持 9100：改 Unity 侧 `Wifi Listen Port` 为 9100 即可，**但建议统一到 9001**，避免和架构文档再次分叉。

## 2. 帧格式

### 2.1 指令帧（B 端 → Unity）

```
+--------+--------+--------+--------+----------+--------+--------+--------+
|  0xAA  |  0x55  |  TYPE  |  LEN   |  DATA... | CHECK  |  0x0D  |  0x0A  |
+--------+--------+--------+--------+----------+--------+--------+--------+
   帧头1    帧头2    类型     长度     数据区     校验     帧尾1    帧尾2
```

| 字段 | 字节数 | 说明 |
|---|---|---|
| 帧头 | 2 | 固定 `0xAA 0x55` |
| TYPE | 1 | 指令帧固定 `0x01` |
| LEN | 1 | **数据区字节数**（指令帧 = 1 或 2） |
| DATA | LEN | 见第 3 节 |
| CHECK | 1 | 1 字节校验，见第 4 节 |
| 帧尾 | 2 | 固定 `0x0D 0x0A` |

- 最短帧 7 字节（数据区为空），指令帧实际是 **8 或 9 字节**。
- **没有 SEQ、没有 ACK**（这是 UDP 链路，和 TCP 那套不同）。
- Unity 端靠 **帧尾 `0D 0A` 定界**，所以数据区里不要出现连续的 `0D 0A`。

### 2.2 长度字段的兼容性

Unity 端**接受三种长度写法**（会自动判断，不一致只记诊断计数，不丢帧）：

| 写法 | LEN 的值 | 是否推荐 |
|---|---|---|
| 数据区长度 | `LEN = N` | **推荐，Unity 自己发出的帧就是这个** |
| 帧体长度 | `LEN = N + 3`（类型+长度+数据+校验） | 兼容 |
| 整帧长度 | `LEN = N + 7`（含帧头帧尾） | 兼容 |

**结论：B 端按"数据区长度"写最省事。**

## 3. 指令帧数据区

### 3.1 结构

```
DATA[0] = 指令码（0x01～0x06）
DATA[1] = 速度 / 转向强度，0～100（可选）
```

- **数据区只有 1 字节**：只发指令码，速度沿用当前值。
- **数据区 2 字节**：先按百分比改速度，再执行动作。
- **数据区 3 字节**：Unity 也接受 `[1..2]` 作为 int16 小端的速度值（兼容写法），但**不建议**，用 2 字节即可。

### 3.2 指令码

| 码 | 含义 | 内部映射 | 备注 |
|---|---|---|---|
| `0x01` | 前进 | Forward | 线速度 |
| `0x02` | 后退 | Backward | 线速度（负方向） |
| `0x03` | 左转 | SteerLeft | 默认"行进中转向"（弧线），不是原地转 |
| `0x04` | 右转 | SteerRight | 同上 |
| `0x05` | 停止 | Stop | 平稳减速停车 |
| `0x06` | 急停 | EmergencyStop | **锁存**，见 6.3 |

- `0x00`、`0x07` 及以上：**忽略**，只记"未知码"计数。
- 左转/右转如果不想要弧线、想要**原地旋转**：Unity 侧把 `TurnMode` 改成 `RotateInPlace` 即可（一个勾选项）。

### 3.3 速度百分比的口径

| 指令 | 100% 对应 | 说明 |
|---|---|---|
| `0x01` / `0x02` | **1.0 m/s** | `MaxLinearSpeed`，可改 |
| `0x03` / `0x04` | **1.5 rad/s**（约 86°/s） | `MaxAngularSpeed`，可改 |

- `0` 或不带该字节 = **不改速度**，按当前速度执行。
- Unity 端还会再套一层安全限幅：线速度不超过 `Safety.SpeedLimit`（默认 1.0 m/s），角速度不超过 `Safety.AngularLimit`（默认 1.5 rad/s）。
- 所以 **50 = 0.5 m/s**，`0x64`（100）= 1.0 m/s。

## 4. 校验算法

### 4.1 推荐：累加和 Sum8

```
CHECK = (TYPE + LEN + DATA[0] + ... + DATA[N-1]) & 0xFF
```

覆盖范围：**从 TYPE 到 DATA 末尾**（不含帧头、不含帧尾、不含 CHECK 本身）。

这是 Unity 端 `EncodeFrame` 的默认写法，也是自动识别时**第一个尝试**的组合。

### 4.2 Unity 端的自动识别能力

收到帧后，Unity 会按下面 6 种组合逐个试，**连续 2 帧命中同一种才锁定**：

| 算法 | 覆盖范围 |
|---|---|
| 累加和 Sum8 | TYPE + LEN + DATA |
| 累加和 Sum8 | 仅 DATA |
| 异或和 Xor8 | TYPE + LEN + DATA |
| 异或和 Xor8 | 仅 DATA |
| CRC8（poly `0x07`，init `0x00`） | TYPE + LEN + DATA |
| CRC8（poly `0x07`，init `0x00`） | 仅 DATA |

- 锁定后如果连续 3 帧对不上，会自动解锁重新识别（防止一开始锁错）。
- **但请不要混用**：联调期间固定一种，否则识别会来回跳。
- **不支持 CRC32**：帧里只有 1 字节校验位，CRC32 需要 4 字节，协议层没有位置放。

### 4.3 参考实现（Python，可直接给 Codex 用）

```python
def sum8(body: bytes) -> int:
    """body = TYPE + LEN + DATA"""
    return sum(body) & 0xFF


def build_frame(cmd: int, speed: int = None) -> bytes:
    data = bytes([cmd]) if speed is None else bytes([cmd, max(0, min(100, speed))])
    body = bytes([0x01, len(data)]) + data          # TYPE=0x01, LEN=数据区长度
    return b"\xAA\x55" + body + bytes([sum8(body)]) + b"\x0D\x0A"
```

## 5. 完整报文示例

以下 CHECK 均按 **Sum8 覆盖 TYPE+LEN+DATA** 计算，可直接抓包比对。

| 动作 | 十六进制 | 长度 | 说明 |
|---|---|---|---|
| 前进 50% | `AA 55 01 02 01 32 36 0D 0A` | 9 | `0x01` 前进，`0x32`=50 |
| 前进 100% | `AA 55 01 02 01 64 68 0D 0A` | 9 | 1.0 m/s |
| 前进（不改速度） | `AA 55 01 01 01 03 0D 0A` | 8 | 沿用当前速度 |
| 后退 30% | `AA 55 01 02 02 1E 23 0D 0A` | 9 | `0x1E`=30 |
| 左转 100% | `AA 55 01 02 03 64 6A 0D 0A` | 9 | 1.5 rad/s |
| 右转 50% | `AA 55 01 02 04 32 39 0D 0A` | 9 | |
| 停止 | `AA 55 01 01 05 07 0D 0A` | 8 | |
| 急停 | `AA 55 01 01 06 08 0D 0A` | 8 | 锁存，见 6.3 |

校验手算示例（前进 50%）：

```
TYPE=0x01, LEN=0x02, DATA=0x01 0x32
0x01 + 0x02 + 0x01 + 0x32 = 0x36   →  CHECK = 0x36
```

## 6. 状态回传帧（Unity → B 端，可选但建议接）

### 6.1 帧结构

```
AA 55 03 0F <15 字节状态> CHECK 0D 0A      （共 22 字节）
```

- TYPE = `0x03`，LEN = `0x0F`（15），CHECK 同样用 Sum8 覆盖 `TYPE+LEN+DATA`。
- **只发给最后发指令的那台机器**，5 Hz。
- B 端如果只做发送、不解析状态，可以忽略；但建议至少抓包确认 Unity 在回帧。

### 6.2 数据区 15 字节

| 偏移 | 字节 | 字段 | 单位 / 说明 |
|---|---|---|---|
| 0 | 1 | 状态标志 | bit0 急停锁存 / bit1 故障 / bit2 步进中 / bit3 正在运动 |
| 1 | 1 | 当前动作码 | 0x01～0x06，0x00 = 其它 |
| 2–3 | 2 | 线速度 int16 小端 | **mm/s**，正 = 前进 |
| 4–5 | 2 | 角速度 int16 小端 | **0.001 rad/s**，正 = 左转 |
| 6–7 | 2 | X 坐标 int16 小端 | **cm** |
| 8–9 | 2 | Z 坐标 int16 小端 | **cm** |
| 10 | 1 | 速度百分比 | 0～100 |
| 11–14 | 4 | 时间戳 uint32 小端 | **ms**，仿真启动以来的单调时间 |

### 6.3 示例

假设：运动中、前进、0.5 m/s、无转向、x=123 cm、z=456 cm、50%：

```
AA 55 03 0F 08 01 F4 01 00 00 7B 00 C8 01 32 60 EA 00 00 CE 0D 0A
```

（`0xF401`=500 mm/s，`0x007B`=123，`0x01C8`=456，`0xEA60`=60000 ms）

## 7. 超时 / 急停 / 持续执行逻辑

这是最容易对接出问题的地方，逐条说清。

### 7.1 链路在线判定：3 秒

- Unity 端 `PeerTimeoutMs = 3000`：**3 秒没收到任何 UDP 包**，就把链路标记为"未连接"。
- 这个标记**只影响 HUD 显示和看门狗判断**，**本身不会让车停下**。
- 之所以不会停，是因为 WiFi 链路的"心跳看门狗"默认关闭（`WifiRequiresHeartbeat = false`）。
  纯本地键盘调试时也是同理，避免误判。

### 7.2 真正的"停发自动停"：指令租期 4 秒

- WiFi 链路默认是 **状态保持式（Latch）**：收到一次 `0x01`，车就一直前进。
- 每次收到运动指令，Unity 会重置一个 **4 秒租期**（`WifiCommandLeaseSeconds = 4`）。
- **4 秒内没有新的运动指令** → 自动平稳减速停车（走 Stop 路径，**不进急停锁存**，可以直接再发指令）。
- 所以 B 端如果要做"按住一直走"，必须**至少每 4 秒重发一次**；任务书里的 0.2 s 重发完全够用。
- 参数类指令（调速度/限速）不会刷新租期。

### 7.3 急停：锁存，且当前 **UDP 无法解除**（重要）

- 收到 `0x06` → `Safety.Latch(...)` + 控制器立即清零 + 中止步进。
- 锁存期间**所有运动指令被忽略**，包括 `0x01`～`0x05`。
- **解除方式目前只有两个**：Unity 端按键盘 `Z`，或走 ASCII 文本指令 `REL`。
- **UDP 指令码表里没有"解除急停"**（0x01～0x06 里没有 0x07），所以 B 端发完急停后**无法自己恢复**。

> 建议：联调时给 UDP 增加 `0x07 = 解除急停`（映射到 `ReleaseEmergency`）。
> 这是本次接口唯一的功能缺口，需要你们确认是否现在加。

### 7.4 两种指令语义，必须二选一

| 模式 | Unity 侧开关 | 行为 | 适合场景 |
|---|---|---|---|
| **Latch（当前默认）** | `WifiStepMode = false` | 收到一次就走，直到 Stop 或 4 秒租期到期 | App 按住式连续控制 |
| **Step（建议脑电用）** | `WifiStepMode = true` | 每条指令走**固定一步**后自动停 | CCA 离散识别输出 |

Step 模式的默认参数：

| 参数 | 默认值 |
|---|---|
| 前进/后退一步 | **1.0 m** |
| 左转/右转一步 | **30°** |
| 步进速度 | 0.30 m/s |
| 步进转速 | 34 °/s |

Step 模式下还有两个**针对脑电的防抖机制**，B 端必须知道：

- **不应期 1.0 s**：同一意图 1 秒内的重复指令会被忽略（防止 CCA 连续输出把一步变成多步）。
- **指令 TTL 5.0 s**：排队超过 5 秒的指令自动丢弃。
- 不同意图可以抢占（`PreemptOnDifferentIntent = true`），即"前进"执行中收到"停止"会立刻响应。

> **给脑电的建议**：把 `WifiStepMode` 勾上。CCA 每次识别输出一个离散动作，用 Latch 会让"前进"直接跑满 4 秒（约 2.4 m），
> 对轮椅来说太危险；Step 模式才是"识别一次 = 走一步"。

### 7.5 可靠性建议

UDP 不保证到达，且没有 ACK：

- **急停 `0x06` 连发 3 次**（间隔 20～50 ms），确保至少一帧到达。
- 运动指令按 5～10 Hz 重发（远高于 1 秒不应期，Step 模式下不会重复触发）。
- 不要依赖状态帧做闭环控制，它只是监视用。

## 8. 与"9100 + CRC32"文档的差异

| 项目 | 架构文档（旧） | **当前 Unity 实现（以此为准）** |
|---|---|---|
| 端口 | 9100 | **9001** |
| 校验 | CRC32（4 字节） | **1 字节，Sum8 / Xor8 / CRC8 自动识别，推荐 Sum8** |
| 帧尾 | 未提及 | **`0D 0A` 定界** |
| 帧内序号 | 未提及 | **无 SEQ** |
| 指令码 | 未明确 | **0x01～0x06** |
| 状态回传 | 未明确 | **0x03，15 字节，5 Hz，9002** |

结论：**以本文件为准**。架构文档那份需要同步修订，否则后面还会有人按 9100/CRC32 写。

### 9.2 联调前检查（Unity 侧）

1. 打开场景 `Main_Editable.unity`（或 `Main.unity`），选中 `Wheelchair`；
2. `Wheelchair Scene Rig` 组件里确认：
   - `Enable Wifi Udp` ✅
   - `Wifi Listen Port` = **9001**
   - `Wifi Status Port` = **9002**
   - `Wifi Step Mode`：脑电建议 ✅；按住式 App 则 ❌
   - `Wifi Command Lease Seconds` = 4
3. Play；
4. Console 应出现 `[SceneRig] 就绪：... 指令源=N ...`；
5. HUD 的"指令来源"里应看到 `WiFi/UDP :9001`，并显示 `收到 X 帧 / 校验 ...`。

### 9.3 联调第一包（最小验证）

先发这一帧（前进 50%）：

```
AA 55 01 02 01 32 36 0D 0A
```

预期：

- HUD "最近指令"变成 `0x01 Forward 50%`；
- 轮椅前进，速度约 0.5 m/s；
- **4 秒后自动停**（因为只发了一次，租期到期）；
- 如果每 0.2 s 重发，则持续前进，直到发 `AA 55 01 01 05 07 0D 0A`。

### 9.4 常见失败原因

| 现象 | 原因 |
|---|---|
| HUD 显示"收到 0 帧" | 端口不对 / 防火墙拦了 UDP 9001 / 发到了 127.0.0.1 但 Unity 在另一台机器 |
| 显示"收到 N 帧"但"指令 0" | 校验不对，或被当成状态帧（TYPE 不是 0x01） |
| "校验失败"计数一直涨 | CHECK 覆盖范围不对（试试只覆盖 DATA，或确认 LEN 写法） |
| 车不动但帧收到了 | 急停锁存（按 Z 解除）、或 `Safety` 障碍物过近 |
| 走 4 秒就停 | **正常**，租期到期；要连续就重发 |

## 10. 需要 B 端确认的三件事

1. **校验固定用 Sum8（TYPE+LEN+DATA）** —— 同意的话我们就按这个写死，不再依赖自动识别。
2. **是否增加 `0x07 = 解除急停`** —— 不加的话，急停后必须人工在 Unity 端按 Z。
3. **指令语义用 Step 还是 Latch** —— 脑电 CCA 建议 **Step（一次一步）**，App 按住式用 Latch。
