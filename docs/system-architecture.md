# 系统总体架构（A → B → C）

本文描述最终部署形态。**A → B 链路的协议已定稿**，见 `udp-protocol.md`；
**B → C 链路目前是草案**，见本文第 4 节，待评审后冻结。

## 1. 拓扑与角色

```
              原始脑电数据流                        控制指令
   手机A  ──────────────────────>  手机B  ──────────────────────>  电脑C
  （热点 AP）                      （信息处理）                    （输出端）
```

| 设备 | 扮演角色 | 硬件 | 软件 | 职责 |
|------|----------|------|------|------|
| **手机 A** | 脑电采集设备（模拟） | Android 手机 | 本项目 App（已是热点 AP） | 读取真实 OpenBMI 数据（62 通道 @ 1000 Hz），按 5 采样点/包推流 |
| **手机 B** | 信息处理设备 | Android 手机 | **待开发** | 接收 A 的原始流，滑窗 CCA 分类出意图，输出方向指令给 C |
| **电脑 C** | 输出端 | PC / Windows | **Unity**（已有 3D 轮椅模型） | 接收 B 的指令，驱动轮椅模型做出对应行为 |

**网络形态**：A 开热点，B 与 C 都连上 A 的热点，三者同处一个网段，可互相单播。
实测地址（本次会话）：

| 项 | 值 |
|----|----|
| 热点网段 | `10.14.166.0/24`（荣耀手机，非常见的 `192.168.43.x`） |
| A（热点 AP 自身） | `10.14.166.241` |
| C（电脑） | `10.14.166.234`（DHCP 分配，**每次重连会变**） |
| 广播地址 | `10.14.166.255` |
| 网络类别 | 公用网络 |

> 因为网段和设备地址都随手机型号、DHCP 变化，**任何一端都不得硬编码 IP 或网段**。
> A 端已经是运行时枚举网卡算广播地址，B、C 端也要遵守同样的原则。

## 2. 两条链路的性质完全不同

| | **A → B**（原始数据） | **B → C**（控制指令） |
|---|---|---|
| 数据量 | 1280 字节/包 × 200 包/秒 ≈ **256 kB/s** | 约 24 字节/次 × 1~5 次/秒 ≈ **几十字节/秒** |
| 语义 | 无状态的采样流 | **有状态**的控制指令 |
| 丢包后果 | 少 5 ms 数据，CCA 几乎不受影响 | **轮椅会保持上一个动作** —— 这是安全问题 |
| 延迟敏感度 | 低（分类器本来就要攒窗口） | 高（用户能感觉到迟滞） |
| 协议状态 | 已定稿（`udp-protocol.md` v2） | 本文草案 |

**核心结论**：A → B 可以容忍丢包，B → C 不能。所以 B → C 必须带**心跳式重复**
和 **C 端安全超时**，不能只在指令变化时才发一次。

## 3. 指令编号（与发送端严格对齐）

B 输出的指令编号**必须**与 A 端 `EegCommands` 完全一致，否则整套方向判定会错位：

| 编号 | 指令 | 刺激频率 | B 端判定依据 |
|------|------|----------|--------------|
| 0 | 停 | 静息，无刺激 | 四个方向相关值**全部低于阈值**（阈值与窗口长度绑定，见 §7.2） |
| 1 | 前进 | 12.00 Hz | 12.00 Hz 分量获胜 |
| 2 | 左转 | 8.57 Hz | 8.57 Hz 分量获胜 |
| 3 | 右转 | 6.67 Hz | 6.67 Hz 分量获胜 |
| 4 | 后退 | 5.45 Hz | 5.45 Hz 分量获胜 |

> 左转 8.57 / 右转 6.67 这两个数是**实测校正过的**，交接文档原表把它俩写反了。
> 证据见 `udp-protocol.md` 第 7 节。频率**不进入任何报文**，只在 B 端做 CCA 参考用。

## 4. B → C 指令协议草案（v1，待评审）

与 A → B 保持同一套设计风格（小端序、固定包头、CRC32 校验），降低实现和排错成本。

| 项 | 取值 |
|----|------|
| 传输层 | UDP（低延迟，无需重传语义） |
| 端口 | `9100`（与数据流 9000、发现 9001 错开） |
| magic | `0x47F0`（线上字节 `F0 47`；与数据流 `0x47EE`、发现 `0x47EF` 区分） |
| 报文长度 | 固定 **24 字节** |

### 4.1 报文布局

| 偏移 | 长度 | 字段 | 说明 |
|------|------|------|------|
| 0 | 2 | magic | 固定 `0x47F0` |
| 2 | 1 | version | `0x01` |
| 3 | 1 | msgType | `0x01` 指令 / `0x02` 信标（C 端广播的「我在这」） |
| 4 | 4 | seq | 报文序号，从 1 起单调递增 |
| 8 | 1 | command | `0`停 `1`前进 `2`左转 `3`右转 `4`后退 |
| 9 | 1 | flags | bit0 = `confidence` 字段有效；其余位保留为 0 |
| 10 | 2 | reserved | 固定 0（为将来扩展位域留位） |
| 12 | 4 | confidence | float32，CCA 获胜相关值（0.0 ~ 1.0） |
| 16 | 4 | windowMs | u32，本次决策所用滑动窗口的长度（毫秒） |
| 20 | 4 | crc32 | 对 `[0, 20)` 计算的 CRC-32 |

### 4.2 B 端发送策略：降频重复，而不是「变了才发」

- 每完成一次决策（建议 200 ~ 250 ms 一次）：
  - **指令发生变化** → 立即发送一包
  - **指令没变** → 降频到 **2 Hz** 继续发送同一指令
- 这样 C 端**只需要一套逻辑**：「记住最近收到的指令」，不用区分心跳包和指令包。

### 4.3 C 端（Unity）实现要点

- **必须回到主线程**：Unity 的 API 不是线程安全的。后台线程只负责 socket 收包并
  塞进 `ConcurrentQueue<byte[]>`，在 `Update()` 里出队处理。
  （在后台线程里直接改 `Transform` 会随机崩溃或静默失效。）
- **安全超时（最重要）**：超过 **1 秒**没收到任何指令 → 强制切到「停」，
  并在界面上提示链路断开。这是轮椅演示的兜底，不能省。
- **切换防抖**：指令切换加最小保持时间（建议 300 ms），避免分类抖动让轮椅抽搐。
- `UdpClient` 需要监听 `9100/UDP`，**Windows 防火墙要放行 Unity 的入站 UDP 9100**。
- 桌面版 Unity 直接用 `UdpClient` 即可；若将来要出 WebGL 版，UDP 不可用，需换 WebSocket。

### 4.4 B 怎么知道 C 的地址（三选一）

| 方案 | 做法 | 评价 |
|------|------|------|
| 1. 手工填 IP | B 的界面上填 C 的 IP | 最省事，但 C 的 DHCP 地址每次重连会变，演示现场容易翻车 |
| 2. **C 端广播信标**（推荐） | C 每 1 秒广播一包 `msgType=0x02` 到 `255.255.255.255:9100`；B 收到即学到 C 的 `address:port`，超过 3 秒没收到即视为 C 下线 | 零配置，C 换 IP 后 B 自动跟上；Unity 侧只需「定期广播」，无需实现请求应答 |
| 3. 完整发现协议 | 复用 `udp-protocol.md` 第 11 节的 DISCOVER/ANNOUNCE | 最规范，但 Unity 的 C# 要自己实现 CRC32 和应答逻辑，工作量最大 |

方案 2 的广播一定从 WiFi 出去：Windows 的默认路由就是手机热点
（`0.0.0.0/0 via 10.14.166.241`），所以 `255.255.255.255` 会命中热点网卡。

## 5. 发现应答的唯一性（必须遵守，否则连错设备）

A 端的自动发现逻辑是「广播 DISCOVER，取**第一个** nonce 匹配的应答」。因此：

- **只有 B 应答 A 在 9001 端口发的发现请求**
- **C（Unity）不得应答 A 的发现请求**
- 用电脑当替身接收端抓包时，必须加 `--no-discovery` 参数，
  否则 B 和 C 会抢答，A 连到哪台纯属竞态

同理，B 找 C 用的是 **9100 端口**，与 A 找 B 的 **9001 端口**完全隔离，不会互相干扰。

## 6. 延迟预算

| 环节 | 耗时 | 说明 |
|------|------|------|
| A → B 网络传输 | 约 2 ms | 同网段 WiFi |
| **B 端窗口填充** | **约 2.5 ~ 4 s** | **全链路主要延迟来源**（见下） |
| B 端决策 + 投票 + 去抖 | 约 0.4 ~ 0.8 s | 4 s 窗每 200 ms 滑一次 |
| B → C 网络传输 | 约 2 ms | 同上 |
| Unity 应用指令 | 1 帧 (约 16 ms) | 主线程出队后立即执行 |

**延迟几乎全部来自 B 端的分析窗口，而且这一次不能靠缩短窗口来降延迟**：按 §7.2 的
定量结论，窗口必须 ≥ 4 s，2 s 窗根本不存在可用的拒识阈值。于是：

- 用户开始注视目标后，窗口里还残留着上一段（通常是静息）的数据，`ρ_true` 要等新
  数据把窗口「冲干净」才会升上来，这个过渡本身就要 2~3 s；
- 首次形成可靠输出 ≈ 窗口填充 `2.5 ~ 4 s`，之后每 200 ms 更新一次；
- **使用要求：一次意图必须连续注视 ≥ 4 s（保守取 5 s）。** 抓包测试时按 0.9 s 能
  验证链路通不通，但**验收识别效果时必须按住 4 s 以上** —— 按不够时长，窗口里
  根本没有足够的目标频率成分，任何算法都判不出来。

要降低操作上的迟滞感，唯一可行的方向是**滑动窗 + 多窗投票 + 去抖迟滞**（已计入
上表），而不是缩短窗口长度。

## 7. 能力边界与数据源性质（重要，演示前必读）

### 7.1 SSVEP 的输出里没有「专注度」

SSVEP 的输出只有两样东西：

1. **类别** —— 用户当前正在注视哪个闪烁目标（即哪个频率）。
2. **置信度** —— 这个判断有多可信。工程上用 **CCA 获胜相关值**度量，就是本方案
   B → C 报文里的 `confidence` 字段（0.0 ~ 1.0）。

**没有「专注度」这个量。** 「专注度 / 放松度」是另一条技术路线的东西：消费级
单通道脑电设备（头环一类）用被动式范式，把 θ/β 或 α 节律的能量比换算成一个
指数。那条路线与 SSVEP 用的信号、范式、算法都不一样，两者不能混为一谈。

但「专注」确实会影响 SSVEP：走神、疲劳、频繁眨眼会让枕区 SSVEP 幅值下降、
相关系数整体走低，表现为更容易判错、或低于阈值被判成「无指令」。
所以**它是影响分类质量的状态因素，而不是一个被输出的指标**。
它不需要单独测量 —— 用户走神时，`confidence` 自己就会掉下来。

### 7.2 不是每次都能正确表达意图

SSVEP 是**概率分类**，不是确定性读心。参考量级：

| 条件 | 典型准确率 |
|------|------------|
| 受试者响应好、刺激设计合理、窗口 2~4 s | 85% ~ 95% |
| 一般受试者、窗口 1~2 s | 70% ~ 85% |
| 「低响应者」（约 10% ~ 30% 的人群） | 可能低于 60%，甚至用不了 |

本项目用真实录制数据做的定量结果（`tools/degrade_reference.py`；9 通道枕顶区、
4~45 Hz 带通、3 次谐波 CCA，非重叠切窗统计）：

| 窗口 | 获胜相关（正确方向） | 次高（第二名方向） | 静息段最高 | 方向段最低 |
|------|---------------------|-------------------|-----------|-----------|
| 4 s | 0.7361 | 0.3760 | 0.5388 | 0.6018 |
| 2 s | 0.7727 | 0.5392 | 0.7065 | 0.6291 |

由此得到的硬结论：**「无指令」阈值只在 4 s 窗下存在**。4 s 时可用区间是
(0.5388, 0.6018)，宽度 +0.0630，取 **θ ≈ 0.57**；而 2 s 窗下静息段的最高相关
（0.7065）**高于**方向段的最低相关（0.6291），区间是负的 —— 任何一个单一阈值
都必然同时切错两侧。

差值门（`ρ_win − ρ_second ≥ θ₂`）结论一致：4 s 时静息最大 0.2107 / 方向最小
0.2783（可行，+0.0676）；2 s 时 0.1817 / 0.0566（同样倒挂）。

> **补充（2026-10-18）**：上表的 `θ ≈ 0.57` 是**本机理想滤波口径**下的值，
> 且是在**与录制试次对齐的窗**上测的。换带通实现或换成真实滑动窗，ρ 会漂移
> **4~9 个百分点**（可用余量只有 0.063），阈值必须重标 —— 见
> `receiver-handbook.md` §5.6，对照实验用 `tools/acceptance_probe.py --filter-check`。

所以 B 端**必须用 ≥ 4 s 的分析窗**。要压低延迟只能靠**滑动窗口 + 多窗投票**
（每 100~200 ms 出一个窗，连续 N 个窗一致才输出），**不能靠缩短窗口长度** ——
2 s 窗不是「准确率差一点」，而是根本不存在可用的拒识阈值。

（注意这组数字来自**离线、特定受试者**的理想条件；真机使用会明显更差。）

因此 B 端必须有四道防线，缺一不可：

1. **置信度阈值** —— 低于阈值判「无指令」，而不是硬猜一个方向；
2. **多窗口投票** —— 连续 N 个窗口一致才输出，滤掉单次抖动；
3. **去抖迟滞** —— 指令切换需持续 ≥ 300 ms；
4. **超时强制停车** —— 1 s 内没收到有效指令就停（安全兜底，不是可选项）。

### 7.3 本项目的脑电数据是「回放」，不是实时采集

**这是必须对演示对象讲清楚的一点。** 当前 A 端推送的是 OpenBMI 数据集里
**预先录制的真实脑电波形**：按住「前进」，推的是 forward 段的真实 SSVEP 数据。

所以接收端判出 forward，**不是因为它读懂了操作者的想法**，而是因为播放的
本来就是 forward 的波形。当前端到端跑通，证明的是：

- 数据通路（采集格式 → 报文 → 网络）正确；
- 报文格式与解析实现自洽；
- B 端 CCA 算法在真实波形上工作正常。

它**证明不了**「能读懂人的想法」。要验证后者，必须把数据源换成**实时采集**：
让使用者真的盯住对应频率的闪烁目标，再用同一套算法统计准确率。那一步才构成
真正意义上的人机接口。

演示与答辩时不要把它描述成「读取脑电、还原想法」。准确的说法是：
**用真实录制的 SSVEP 数据，验证从采集设备到指令输出的完整链路与识别算法。**

### 7.4 SSVEP 能做什么、不能做什么

| 能做 | 不能做 |
|------|--------|
| 从**少数几个固定选项**里选一个（盯着哪个灯） | 自由表达想法、连续控制（走位、调速） |
| 稳定输出离散指令（本项目 5 个：前进/后退/左转/右转/停） | 快速输入（一次选择需 1~4 s，且不能长时间保持） |
| 配合去抖与超时兜底，做到「能停下」 | 不看屏幕的盲操作（SSVEP 依赖视觉注意） |

轮椅场景之所以成立，正是因为**它只需要少数离散指令**，恰好落在 SSVEP 的能力
范围内。但它的真实产品定位是「重度运动障碍者的辅助操作手段」，
不是「人人可用的通用操控方式」。

### 7.5 A 端内置的「人为降质」开关（B 端标定用）

A 端界面上有两个滑块，用来**故意把 B 端算出的相关值压下来**，让 B 端能在没有
「真的走神」的情况下标定阈值、验证拒识行为。两者都在**信号层**生效，报文格式
一个字节都不改，B 端根本感知不到（不允许通过协议告知 B 端）。

| 滑块 | 做法 | 效果 | 用途 |
|------|------|------|------|
| 信号干扰（噪声） | `x' = x + α·rms·N(0,1)` | `ρ_true` 与 `ρ_rest` **同步下降**，方向开始判错 | 测**拒识安全性**：信号差时会不会乱下指令 |
| SSVEP 削弱（陷波） | 4 个刺激频率的 1~3 次谐波谱线乘 `(1−α)` | `ρ_true` 陡降、`ρ_rest` 几乎不动，方向仍判对 | 标定**「无指令」阈值**：把 ρ 压到 θ 以下看是否判停 |

滑块刻度按 **4 s 窗实测曲线**标定：100% = 完全不处理（`ρ≈0.736`），0% ≈ `ρ=0.30`。
**这组刻度只对 4 s 窗成立** —— 换成 2 s 窗，同一个百分比会得到明显更高的 ρ（§7.2）。

B 端标定阈值时的推荐动作：把「SSVEP 削弱」往下拖，直到 ρ 刚好跌破自己设的 θ，
确认输出从方向变成「无指令」，再拖回来确认恢复 —— 这是阈值选没选对的直接证据。
