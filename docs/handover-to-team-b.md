## 0. 先看这五句

1. 你们做的是**接收端 App**：从 A 端手机收原始脑电流 → 自己做 CCA 分析 → 把「前进 / 后退 / 左转 / 右转 / 停」发给 C 端 Unity 轮椅。
2. **A 端已经做完，协议冻结了。** 你们不需要改协议，只需要按协议解析。
3. **A 端不发「频率」，也不发任何「意图」。** 它只发原始 62 通道波形 + 时间戳，所有解码都在你们这边。
4. **最危险的不是算错，是收不到。** Android 上「一包都没收到」的第一嫌疑人永远是 **MulticastLock 没持**，不是网络不通（见 §2.1）。
5. **`θ₁=0.63` 不能照抄。** 它是我们机器上的值，换滤波器/窗长就漂移，而且漂移量比可用余量还大。必须自己重标（见 §6）。

## 1. 你们的任务（一句话）

**手机 B 连上手机 A 的热点，收下 A 发来的 62 通道 @1000 Hz 原始脑电流，每个 4 秒试次用锚定在试次头的 3 秒数据判一次「用户想去哪」，把结果发给 C 端的 Unity 轮椅模型。**

链路：

```
A 手机（发送端，已交付）
   │  热点：A 自己就是 AP / 网关
   │  UDP 单播 → 9000 端口（数据流）
   │  UDP 广播 → 9001 端口（发现：A 广播 DISCOVER，B 应答 ANNOUNCE）
   ▼
B 手机（接收端  ← 你们做的）
   │  UDP → 9100 端口（指令流，草案）
   ▼
C 电脑（Unity 轮椅模型  ← 别人做的）
```

## 2. 你们必须做到什么（核心清单）

下面每一条都是**验收项**，建议逐条打勾。

### 2.1 网络与发现 ★最容易全盘翻车

这几条不做，现象是「A 明明在发，B 一包都没收到」，然后你们会花两天排查网络，其实是权限没给。

- [ ] **持 `MulticastLock`**（`WifiManager.createMulticastLock`）：进入监听就 `acquire()`，退出才 `release()`。
      Android 的 WiFi 芯片默认把广播/组播包直接丢掉，只有拿了 MulticastLock 才会上送给 App。
      现象：A 在广播 DISCOVER，B 完全没反应。
- [ ] **监听跑在「前台服务」(Foreground Service) 里，带常驻通知。**
      不这么做，息屏几分钟后系统会掐掉你的 socket 或冻结进程，表现是「用着好好的，锁屏一会儿就断了」。
- [ ] **在 9001 端口应答 DISCOVER，而且「广播」和「单播」两种都要应答。**
      有些机型不会把广播发给每个客户端。你们必须两种都处理：收到**广播** DISCOVER 要回，收到**定向发给你们 IP** 的 DISCOVER 也要回。
- [ ] **`nonce` 原样回显**（从 DISCOVER 里读出来，原封不动写进 ANNOUNCE）。A 靠 nonce 匹配「这个 ANNOUNCE 是回给我这次广播的」。
- [ ] **ANNOUNCE 里填自己的数据端口（`dataPort`），不要填 IP。**
      A 从 UDP 包的**源 IP + 源端口**自己学你们的地址，不需要你们在包里写 IP。
- [ ] **只有 B 应答发现；C 端（Unity）绝对不许应答 9001 的广播。**
      如果你们把 B 和 C 跑在同一台电脑上，必须给 C 加 `--no-discovery`（或等价开关）。
      否则 A 会收到两个 ANNOUNCE，分不清哪个是 B。
- [ ] **加 `WifiLock`（`WIFI_MODE_FULL_HIGH_PERF`）**，避免息屏时 WiFi 省电降速。

### 2.2 协议解析

权威文档：`docs/udp-protocol.md`。这里只列**你们必须实现**的部分。

- [ ] 解析 A→B 的 **v2 通用包头 16 字节**：
      `magic u16 = 0x47EE`（线上是 `EE 47`）｜`version u8 = 2`｜`msgType u8`｜
      `deviceId u32 = 0x45454731`（"EEG1"）｜`seq u32`｜`payloadLen u32`。
      全部**小端**。整包长度 = `16 + payloadLen + 4`。
- [ ] 解析末尾 4 字节 **CRC32**（IEEE 802.3 / zlib），覆盖范围 `[0, 16+payloadLen)`。**CRC 不过就丢包，不要用**。
- [ ] 实现三种报文：

  | msgType | 名字 | 内容 |
  |---|---|---|
  | `0x01` | `STREAM_INFO` | `sampleRate u32 / channelCount u16 / dataType u8=0x01(float32) / reserved u8 / namesLen u16 / 通道名(UTF-8 逗号分隔)`。推流开始时发一次。 |
  | `0x02` | `SAMPLE_BLOCK` | `firstSampleIndex u64 / deviceTimeUs u64 / sampleCount u16 / channelCount u16 / samples`。samples 为 **float32 小端、时间主序**。 |
  | `0x03` | `STREAM_STOP` | `lastSampleIndex u64 / reason u8`（`0x01`=正常结束 / `0x02`=错误 / `0x03`=切换指令）。**松手收尾时 A 端会发**（`reason=0x01`），换方向打断时不发 —— 两种都要处理，见下条。 |

- [ ] **以 `STREAM_INFO` 里的 `sampleRate` / `channelCount` / 通道名为准**，**不要硬编码 1000 / 62 / 通道顺序**。通道名是逗号分隔的 UTF-8 字符串。
- [ ] 每个报文的**第一个采样点在整段流里的下标**来自 `firstSampleIndex`，用它对齐/去重；`deviceTimeUs` 是设备侧时间戳（微秒）。
- [ ] 发现子协议（端口 `9001`，magic `0x47EF`，version `1`）：
  - `DISCOVER` 固定 **16 字节**，`struct '<HBBIII'`：magic u16 / version u8=1 / msgType u8=0x01 / nonce u32 / deviceId u32 / crc32（覆盖 `[0,12)`）。
  - `ANNOUNCE` = **13 + nameLen + 4** 字节，`struct '<HBBIHHB'`：magic u16 / version u8=1 / msgType u8=0x02 / nonce u32 / **dataPort u16** / reserved u16=0 / nameLen u8(0..40) / name(UTF-8) / crc32（覆盖 `[0, 13+nameLen)`）。
  - 收到 DISCOVER 到发 ANNOUNCE **越快越好**（A 侧超时 2 s、重试 3 次）。
- [ ] **A 的发送节奏**（用于估缓冲）：`MAX_DATAGRAM=1472`，每包 5 个采样点，报长 1280 字节，200 包/秒（5 ms 节拍），稳态带宽 ≈ 256 kB/s。**必须无阻塞地持续收**，否则内核缓冲会溢出丢包。
- [ ] **长度不固定：交互是「按住方向键一直发、松手才结束」。**
      A 端不再自动推固定 4 秒，长度完全由手指决定（按住 6 秒就是 6000 采样点 = 1200 个
      `SAMPLE_BLOCK`）。起流同时发 `STREAM_INFO`。
- [ ] **两种收尾，都要当硬边界：**
      **松手**（`ACTION_UP`/`ACTION_CANCEL`）→ 补发一个 `STREAM_STOP`（`reason=0x01`），
      收到即收窗定稿，不必再等静默；
      **换方向被打断** → **不发** `STREAM_STOP`，紧接着就是新一路的 `STREAM_INFO`。
      **仍然要留静默超时兜底**（建议 ≥200 ms 收不到 `SAMPLE_BLOCK`）：界面退到后台时
      A 端是**静默**打断的，什么报文都不会发。
      **别把「等不到结束报文」当成丢包或断线。**
- [ ] **`STREAM_INFO` 就是「上一路已结束」的硬边界：收到它就必须清空当前缓冲、重新计时。**
      这条是**无条件**的 —— 不管上一路是**松手正常收尾**的，还是**被中途打断**的。
      按住期间改按另一个方向时，A 端的规则是：
      **按下同一方向** → 事件重发，**视作没按**，被忽略（**不会**出现新的 `STREAM_INFO`）。
      **按下别的方向** → **立刻打断**当前这一路（**不发任何收尾报文**），随即开一路全新的流。
      所以**被丢弃的那一路长度可能远不足 3 秒、且没有结束标记**：不要假设「一定能攒满 3 秒再出结果」，
      必须让静默超时兜底。反过来，`STREAM_INFO` 一到就要立刻丢掉尚未成形的旧窗，
      **别让上一路的残留数据混进新试次**（这是最容易出的错：把两路拼进同一个 3 秒窗）。

### 2.3 信号处理

- [ ] **按「通道名」取 9 个枕顶通道，不要按下标。**
      这份数据集里的下标是 `Pz=24, O1=28, Oz=29, O2=30, P1=41, P2=42, POz=43, PO3=60, PO4=61`，
      **但取数时请从 `STREAM_INFO` 的通道名里按名字找**，不要信下标。
      注意：**PO7 / PO8 不在这份 62 通道布局里**，找不到就跳过（我们实测也只用 9 个）。
- [ ] **4~45 Hz 带通，对连续流做，滤波器状态跨包保留。**
      不要对每个窗单独从头滤波 —— 会有边界瞬态，实测把静息段相关值抬到危险区间（见 §6）。
- [ ] 参考信号：**sin/cos，1/2/3 次谐波，共 6 列，不要 DC 列**（标准 CCA，非 FBCCA）。
      参考频率在你们**本地**：`forward=12.00 / left=8.57 / right=6.67 / backward=5.45 Hz`。
      **这些频率不进任何报文**，只存在你们代码里。
- [ ] 每个方向一个候选频率，跑 CCA 取最大相关值的方向为获胜方向。

### 2.4 意图判定（窗长与对齐方式都是硬约束）

- [ ] **窗长必须 ≥ 3 秒，且窗口必须锚定在试次头上**（`firstSampleIndex mod 4000 == 0`
      起取前 3000 点）。每个 4 秒试次取一个窗，尾部 1000 点丢弃。
      用真实录制数据定量统计过：**2 秒窗下静息段最高相关（0.7065）高于方向段最低相关（0.6291）**，
      即**不存在任何一个阈值能把「有指令」和「没指令」分开** —— 2 秒窗不是「准确率差一点」，
      而是**数学上做不到「无指令」判定**。
      **自由滑动窗（定时取缓冲尾部）同样无解**：任意窗长下绝对门区间都为负
      （`win_compare_v4.py` 实测 2.0~4.0 s 全倒挂），因为 A 端波形是 4 s 试次硬回绕，
      跨试次/跨回绕边界的窗有相位跳变。压延迟只能靠**锚定窗 + 多窗投票**，不能靠缩短窗长或自由滑动。
- [ ] **决策节拍**：窗口填满（≈3 s）后出**第一**个判决；之后每到一个试次头（约每 4 s）
      出一个新锚定窗 → 一次判决。**没有「每 200~300 ms 出一个窗」这回事。**
- [ ] **双门控**（两个条件同时满足才输出指令）：
  1. **绝对门**：获胜方向相关值 > `θ₁`；
  2. **差值门**：获胜方向相关值 − 次高方向相关值 > `θ₂`。
  两者任一不满足 → 输出「停」。
- [ ] **投票**：连续 N 个锚定窗判决一致才输出（建议 N=2~3；注意 3 窗 ≈ 12 s，
      演示/验收场景建议用 **2 窗**或**对首窗直接采纳**，见 `receiver-handbook.md` §6.4）。
- [ ] **去抖 + 超时**：输出稳定后再发指令；一段时间内无有效判决 → **主动发「停」**（fail-safe）。
- [ ] **急停**：提供人工急停，任何时刻能立刻让 C 端停。

### 2.5 阈值 —— 必须自己重标（见 §6）

- [ ] `θ₁ ≈ 0.63`、`θ₂ ≈ 0.171` **只能当起点**，不能当常数。
- [ ] **必须用你们自己的滤波器、在你们自己的静息段上重新标定**，方法见 §6 与 `docs/receiver-handbook.md` §5.6。
- [ ] 标定结果必须写进你们自己的文档，并注明**前提条件**（窗长、带通实现、对齐方式）。

### 2.6 输出给 C 端（草案，实现前先和 C 组对齐）

权威草案：`docs/system-architecture.md` §4。

- [ ] UDP → 端口 `9100`，magic `0x47F0`（线上 `F0 47`），**固定 24 字节**。
- [ ] 字段含：指令（前/后/左/右/停）、`flags`（bit0 = confidence 有效）、
      `confidence`（= **CCA 获胜方向的相关值**，**不是**「专注度」之类心理量）、`windowMs`。
- [ ] **变化即发 + 未变化 2 Hz 心跳 + 双端 1 s 安全超时**（收不到就停）。
- [ ] 推荐方案：C 端每秒广播一次信标，B 端 3 秒收不到信标就认为 C 下线。

## 4. 关于「B 手机连 A 的热点，到底能不能收到 A 发的包？」

**能，而且这是推荐做法。**

原因：**A 开热点时，A 自己就是网关（典型 `192.168.43.1`）。** B 连上后拿到同网段 IP（`192.168.43.x`）。
A → B 的**单播 UDP**，本质是「热点主机 → 客户端」，**直通**，不受 AP isolation（客户端隔离）影响。
你们不需要任何额外网络配置，只需保证：

1. 按 §2.1 拿到 MulticastLock（收**广播**才需要；单播本身不需要 —— 但走自动发现就必须要）；
2. 监听跑在前台服务里；
3. App 的 socket 正常绑定即可（Android 上通常不涉及系统防火墙）。

**方向容易搞反**，这里说清楚：**A 是发送方，B 是接收方，所以是 A 需要知道 B 的地址。** 两条路：

| 路径 | 怎么用 | 什么时候用 |
|---|---|---|
| **① 自动发现**（推荐） | A 往 `9001` 广播 `DISCOVER` → B 回 `ANNOUNCE`（带自己的 `dataPort`）→ A 从**源 IP** 学到 B 地址，开始发 `9000` | 日常用，**B 的 IP 变了也不用改配置** |
| **② 定向直发**（兜底） | 人工在 A 的界面填 B 的 IP，A 直接发 `9000` | 自动发现失败的机型，或调试时 |

**B 的 IP 怎么看**（需要手工填时）：手机 B → 设置 → 关于手机 → 状态信息 → IP 地址。

> ⚠️ **IP 填错 A 是检测不到的**（UDP 无回执），A 界面会显示「发送成功」但 B 一包都收不到。
> 这是已知限制，当前不打算做探测确认。**所以优先用自动发现。**

## 5. 关于「降质」（A 端有一个测试滑块）

A 端界面上有**一个**滑块（**信号置信度**，内部是陷波降质），默认 **100% = 不处理**，往下拖才是降质。
A 会在**信号层**削弱 SSVEP（另有加噪路径但**未暴露到 UI**，只用于标定脚本与单元测试），
但**报文格式完全不变，也不会通知你们**。

**你们的 App 不需要为它做任何特殊处理**，但要知道：

- 这是给你们**测试阈值鲁棒性**用的；
- **滑块（陷波）**用来**标定阈值**（它让 SSVEP 变弱，但实测**从不判错方向**）；
- 无论滑块拖到哪，**「判错方向」必须始终 = 0** —— 这是最重要的安全底线；
- **翻转点 ≈ 滑块 76%**：按住「前进」一边把滑块从 100% 拖到 0%，判决应在**拖动过程中**
  从 forward 连续过渡到「停」（不是松手后才变）。76% 附近是「方向最低 ρ 跌破静息最高 ρ」的档位。

## 6. 阈值为什么不能照抄（这一条最容易翻车）

`θ₁ = 0.63` 这个数是在**我们这台机器、用我们的滤波器实现**算出来的。它只在**三个前提**同时成立时才有效：

1. **3 秒窗且锚定试次头**（2 秒窗无解、自由滑动窗全倒挂，见 §2.4）；
2. **理想的 4~45 Hz 带通**（普通 rfft 掩码）；
3. **窗与录制试次对齐**。

任何一条偏离，相关值就会漂 **4~9 个百分点**，
而 3 秒窗下**可用余量总共只有 0.106**（可用区间 `(0.5783, 0.6845)`）。

**结论：偏移比余量还大，照抄必踩坑。**

我们实测的带通口径对照（3 s 锚定窗，`θ₁=0.63`；IIR/filtfilt 三行是早期 4 s 实测，趋势相同）：

| 带通实现 | 方向最低 | 静息最高 | 结果 |
|---|---|---|---|
| 普通 rfft 掩码（我们的参考口径） | 0.6845 | 0.5783 | ✅ 可用 |
| 逐窗 IIR 2 级（4 阶 Butterworth） | 0.6293 | **0.5685** | ⚠️ 余量仅 **0.0015**（早期 4 s 实测） |
| 逐窗 IIR 3 级 | 0.6480 | **0.5997** | ❌ 静息被击穿（早期 4 s 实测） |
| 逐窗 `filtfilt`（双向） | 0.6725 | **0.6162** | ❌ 静息被击穿（早期 4 s 实测） |

（2 秒窗重复同一实验：四种口径**全部击穿**，静息最高 0.7146~0.7672。）

**所以你们必须自己在自己的静息段上重标**，步骤（详见 `receiver-handbook.md` §5.6）：

1. **冻结实现**（滤波器、窗长、对齐方式都定下来）；
2. 录**至少 30 秒静息**（不看刺激、放松），切窗算出**静息最高相关**；
3. 每个方向**按住 3 秒以上再松手、重复几次**，算出**方向最低相关**；
   每次**松手后等收尾报文（`STREAM_STOP`）到齐再做下一次** —— 标定期间不要在按住
   中途改按别的方向（那会打断当前这一路，变成一条没有收尾报文的新流）。
4. 取中点作 `θ₁`；要求两个分布**不重叠、区间宽 ≥ 0.03**；
5. 把标定结果和**前提条件一起写下来**（换实现就重标）。

> 更省事的办法：直接用验收器 `tools/acceptance_probe.py` 的 `--filter-check` 模式，
> 它会把「同样的数据、不同滤波口径」的门控结果并排打出来，你可以照着自己的实现对比。

## 7. 怎么证明你做对了（验收）

### 7.1 分级验收

| 级别 | 怎么测 | 通过标准 |
|---|---|---|
| **L1 协议** | 用真实抓包（`.pcap` 或 `udp_probe.py`）喂给解析器 | `STREAM_INFO` / `SAMPLE_BLOCK` 解析正确、CRC 通过；**松手时的 `STREAM_STOP`（`reason=0x01`）能正确收尾**；**换方向被中途打断时（没有 `STREAM_STOP`），紧跟其后的那条 `STREAM_INFO` 能立刻清空缓冲**（前一路长度任意、也必须处理对）；**静默超时**也保留，用于界面退到后台那种静默结束 |
| **L2 发现** | A 端手机开热点、开广播；B 连上 | B 在 3 秒内回出 ANNOUNCE，A 自动学到 B 地址并开始发流 |
| **L3 静默** | 用户放松不看刺激 ≥ 30 秒 | 输出恒为「停」，**不得出现任何方向** |
| **L4 方向** | 每个方向按住 3 秒以上再松手、重复几次；另外特意测一次「按住途中改按别的方向」，以及一次「按住时把降质滑块从 100% 连续拖到 0%」 | 4 个方向都能稳定判出，切换有去抖、不抖；**按住中途改方向时旧窗被立刻丢弃、新试次从头开始**（不得把两路拼成一个窗）；**拖动滑块时判决应在拖动过程中连续变化**（翻转点在滑块 ≈76%），而不是松手后才变 |
| **L5 降质** | A 端滑块从 100% 拖到 0% | **「判错方向」始终 = 0**；判不出时输出「停」，不是乱判 |
| **L6 长跑** | 连续运行 30 分钟，含息屏 | 不崩、不断流、内存不涨 |

## 8. B 端 App 还没写出来时，怎么先跑通链路

**今天就能跑**：用电脑当 B。

1. 手机 A（发送端）开热点、启动发送；
2. 电脑连上 A 的热点；
3. 电脑上跑我们的**抓包 / 会话验收工具**：

```powershell
cd D:\EEGSender
$env:PYTHONIOENCODING="utf-8"
py -3 -u tools\udp_probe.py --name PC-Receiver --seconds 900
```

它会：应答 9001 的发现 → 收 9000 的流 → 逐包校验 magic / version / payloadLen / CRC-32 →
跟踪 `STREAM_INFO → SAMPLE_BLOCK*` 的**会话边界** → 统计丢包 / 重复 / 乱序、实际包速率与带宽 →
（默认）对收到的数据跑 CCA 反推方向。**这就是 B 端协议层的一个可用参考实现**（Python，非 Android），
你们可以照着它对行为。等 B 端 App 写出来，**A→B 协议一个字都不用改**，手机对手机是同一套东西。

> `--seconds 900` 表示「15 分钟后自动退出」，不写则常驻。调试期间建议写上，
> 免得进程残留占住 9000 端口，导致下一次启动绑不上。
> 跑起来后如果先看到 `[DISCOVER] … 已应答 ANNOUNCE`，说明发现链路是通的。

其它有用的模式：

```powershell
py -3 -u tools\udp_probe.py --no-discovery     # 不应答发现（此时 A 端必须手填 IP）
py -3 -u tools\udp_probe.py --no-cca           # 只看协议与会话边界，跳过 CCA
py -3 -u tools\udp_probe.py --save out.npy     # 把收到的采样存成 float32 矩阵
```

> ⚠️ **暂时不要用 `tools\acceptance_probe.py` 的默认模式**：它正在改造中（会话切窗逻辑未完成），
> 直接跑会抛 `NameError`。它的**离线模式不受影响**，可以正常用来对照基线数字：
>
> ```powershell
> py -3 -u tools\acceptance_probe.py --selftest        # 自检
> py -3 -u tools\acceptance_probe.py --verify          # 对照基线数字
> py -3 -u tools\acceptance_probe.py --filter-check    # 对比不同滤波口径的门控结果
> ```
