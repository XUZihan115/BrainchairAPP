# 接收端开发手册（B 端：从原始脑电流到轮椅指令）

> 版本：v1（2026-10-18）
> 读者：负责实现 **B 端（信息处理设备）** 的人或 AI
> 上游输入：A 端发送的 UDP 脑电流，格式见 `udp-protocol.md`（v2，已定稿）
> 下游输出：B → C 的指令报文，格式见 `system-architecture.md` §4（草案 v1）
> 本机环境：Windows + Python 3.14 + numpy（无 scipy，示例代码已尽量规避）

## 0. 怎么用这份文档

B 端要干的事，一句话：

> **收 A 端的 62 通道 @1000 Hz 原始脑电流 → 每 200 ms 用最近 4 s 数据判一次
> 受试者想往哪走 → 把「前进/后退/左转/右转/停」发给 C 端的 Unity 轮椅模型。**

三份文档的分工：

| 文档 | 作用 | 什么时候看 |
|------|------|-----------|
| `udp-protocol.md` | **A → B 的字节格式**（权威，已定稿） | 实现收包解析时逐字段对照 |
| 本文 `receiver-handbook.md` | **B 端怎么实现**（算法、参数、验收、工程坑） | 从第 2 节顺序往下读 |
| `system-architecture.md` | 总体架构、B → C 协议草案、能力边界 | 实现发指令（§7）与做演示说明时看 |

**如果时间有限**，按这个顺序读：§2（总览表）→ §3.2/§3.3（最容易翻车的三条）
→ §5.2（CCA 实现）→ §6（阈值与状态机）→ §9（怎么验收）。

三条**必须**先记住的结论，都是实测出来的，不要凭直觉推翻：

1. **分析窗口必须 ≥ 4 s。** 2 s 窗不存在任何可用的「无指令」阈值（§6.1）。
2. **`θ₁=0.57` 不是通用常数**，它只在三条前提同时成立时才有效：4 s 窗、
   理想的 4~45 Hz 带通、窗与录制试次对齐。换带通实现或换成真实滑动窗，
   ρ 会移动 **4~9 个百分点**，而可用余量总共只有 `0.0630` —— 偏移比余量还大。
   所以阈值**必须用 B 端自己的滤波器、在自己的静息段上重标**（**§5.6**）。
   *（早期草稿里写的「对每个窗单独带通会让 ρ 虚高 10 个百分点以上」经实测
   **不成立**，已作废；真正的风险是滤波器陡度，见 §4.1 的澄清。）*
3. **Android 不持 `MulticastLock` 就收不到 A 端的发现广播**，现象是「一条包都
   没收到」，极易误判成网络不通（§3.3）。

## 1. 任务与验收标准

### 1.1 输入 / 输出

| 项 | 内容 |
|----|------|
| 输入 | UDP 单播流，默认端口 `9000`（实际端口由 A 端发现应答的 `dataPort` 决定）；62 通道、1000 Hz、float32、每包 5 采样点、200 包/秒、1280 字节/包 |
| 输出 | UDP 单播指令，端口 `9100`、magic `0x47F0`、固定 24 字节；`command ∈ {0,1,2,3,4}` |
| 决策节拍 | 每 `200 ms` 出一次判决（窗口长 4 s，重叠 3.8 s） |
| 首次输出 | 开始注视后约 `2.5 ~ 4 s`（窗口填充时间，见 §6.3） |

### 1.2 验收标准（可量化，按本项目数据）

| 指标 | 目标 | 说明 |
|------|------|------|
| 四个方向判对率 | 100%（16/16 窗） | 不降质基线下的离线结果（§5.3） |
| 静息段误判成方向 | 0/2 窗 | 静息必须落在阈值下方 |
| 「无指令」阈值 | 存在且不重叠 | 4 s 窗：区间 `(0.5388, 0.6018)`，取 `θ=0.57`。**该值绑定前提，不可照抄，见 §5.6** |
| 超时停车 | ≤ 1 s 生效 | C 端兜底，B 端也要有 |
| 端到端动作延迟 | ≤ 4.5 s | 从「开始注视」到轮椅动作 |

> 这组数字来自**离线、单一被试、固定条件**（`sess01_subj01`），是「通路正确性」
> 的证据，**不是**「真人使用时的准确率」。真人使用会明显更差，见 §13。

### 1.3 明确不做的事

* **不做实时 EEG 采集**：数据源是 A 端回放的真实录制波形（`system-architecture.md`
  §7.3）。B 端不需要采集设备、不需要电极。
* **不输出「专注度」**：SSVEP 里没有这个量（§7.1）。输出只有「哪个方向」+
  「多可信」。不要为了让界面好看去编造一个 0~100 的「专注度」数字。
* **不做「读心」宣传**：判出 forward 是因为 A 端播的就是 forward 波形。

## 2. 处理流水线总览

```
   ┌──────────────────────────────────────────────────────────────────┐
   │ ① 收包线程                                                       │
   │   socket(9000) → 校验 magic/version/CRC → 解析 SAMPLE_BLOCK      │
   │   → 按 firstSampleIndex 写入环形缓冲（62 通道 × 30 s）           │
   └───────────────────────────┬──────────────────────────────────────┘
                               │ 环形缓冲（原始信号，float32）
   ┌───────────────────────────▼──────────────────────────────────────┐
   │ ② 流式带通 4~45 Hz（IIR，状态跨包连续）                          │
   │   → 滤波结果写入第二个环形缓冲（已滤波信号）                     │
   └───────────────────────────┬──────────────────────────────────────┘
                               │ 已滤波缓冲
   ┌───────────────────────────▼──────────────────────────────────────┐
   │ ③ 决策线程（每 200 ms 醒一次）                                   │
   │   取最近 4000 点 × 9 个枕顶通道 → 对 4 个候选频率做 CCA          │
   │   → 得 ρ(12.00) ρ(8.57) ρ(6.67) ρ(5.45)                          │
   └───────────────────────────┬──────────────────────────────────────┘
                               │ 4 个相关系数
   ┌───────────────────────────▼──────────────────────────────────────┐
   │ ④ 判决层                                                         │
   │   双门控（绝对门 + 差值门）→ 多窗投票 → 去抖迟滞                  │
   │   → command ∈ {0..4} + confidence                                │
   └───────────────────────────┬──────────────────────────────────────┘
                               │
   ┌───────────────────────────▼──────────────────────────────────────┐
   │ ⑤ 发送线程 → 9100/UDP → C 端 Unity                               │
   │   变化立即发；未变化时 2 Hz 心跳                                  │
   └──────────────────────────────────────────────────────────────────┘
```

### 参数速查表（照这个表实现，数值都有依据）

| 参数 | 取值 | 依据 / 备注 |
|------|------|-------------|
| 采样率 | 1000 Hz | A 端固定；应从 `STREAM_INFO` 读取，别写死 |
| 通道数 | 62 | 同上，从 `STREAM_INFO` 读 |
| **分析窗口** | **4000 点（4 s）** | §6.1 定量结论，不可缩短 |
| 决策步进 | 200 ms | 滑动窗，重叠 3.8 s |
| 参与分类的通道 | **9 个**（见 §3.5） | 枕顶区：Pz/O1/Oz/O2/P1/P2/POz/PO3/PO4 |
| 带通 | 4 ~ 45 Hz | 与标定口径一致；**换滤波器实现必须重标阈值**（§5.6） |
| 谐波数 | 1、2、3 次（参考信号 6 列） | 与标定口径一致 |
| 候选频率 | 12.00 / 8.57 / 6.67 / 5.45 Hz | 见 §5.1，**left/right 别弄反** |
| 绝对门 `θ₁` | **0.57**（**仅作起点**） | 4 s 窗不降质基线中点；上线前须按 §5.6 在自己的实现上重标 |
| 差值门 `θ₂` | **0.245**（**仅作起点**） | 4 s 窗，`ρ_top1 − ρ_top2`；同样须重标（§5.6） |
| 投票窗数 | 连续 3 窗一致 | 建议起点，需要实测微调 |
| 去抖迟滞 | 300 ms | 指令切换的最小保持时间 |
| 安全超时 | 1000 ms | 无有效指令即判「停」 |
| 环形缓冲长度 | ≥ 30 s | 至少容得下几个窗口，便于排错与回溯 |

## 3. 接入 A 端数据流

### 3.1 两种连接方式（B 端必须都支持）

| 方式 | A 端界面操作 | B 端要做什么 |
|------|--------------|--------------|
| **自动发现**（推荐） | IP 框**留空** | 监听 `9001/UDP`，收到 `DISCOVER` 就回 `ANNOUNCE`（§3.2） |
| **定向直发** | 手填 B 的 IP | 什么都不用做，直接在 `9000` 收数据即可 |

自动发现是零配置的，演示时不容易翻车（B 的 DHCP 地址每次重连都会变）。
**所以 `9001` 的应答一定要实现**，否则用户只能靠手输 IP。

### 3.2 B 端必须应答 `9001`，而且不只应答广播

A 端的发现流程是「广播 `DISCOVER` → 收 `ANNOUNCE`」，字段定义见
`udp-protocol.md` §11.3 / §11.4。B 端实现要点（照抄这段逻辑即可）：

```python
DISCOVERY_PORT = 9001
MY_DATA_PORT   = 9000      # 必须与你在 ANNOUNCE 里声明的一致
MY_NAME        = "B-接收端"  # 仅用于 A 端界面显示

DISCOVERY_MAGIC = 0x47EF
DISCOVERY_VERSION = 1

def handle_discovery(sock):
    pkt, src = sock.recvfrom(2048)          # src = (A的IP, A的临时端口)
    if len(pkt) != 16:                      # DISCOVER 固定 16 字节
        return
    magic, ver, mtype, nonce, device_id, crc = struct.unpack("<HBBIII", pkt)
    if magic != DISCOVERY_MAGIC or ver != DISCOVERY_VERSION or mtype != 0x01:
        return
    if binascii.crc32(pkt[:12]) & 0xFFFFFFFF != crc:
        return
    name = MY_NAME.encode("utf-8")[:40]              # 上限 40 字节
    # 头部恰好 13 字节: magic(2) version(1) msgType(1) nonce(4)
    #                 dataPort(2) reserved(2) nameLen(1)
    payload = struct.pack("<HBBIHHB", DISCOVERY_MAGIC, DISCOVERY_VERSION, 0x02,
                          nonce, MY_DATA_PORT, 0, len(name)) + name
    assert len(payload) == 13 + len(name)
    reply = payload + struct.pack("<I", binascii.crc32(payload) & 0xFFFFFFFF)
    sock.sendto(reply, src)                 # 单播回「源 IP : 源端口」
```

两个容易漏的点：

* **`nonce` 必须原样回显**，A 端靠它把应答和自己的请求对上号。回错 = 发现失败。
* **`name` 按 UTF-8 边界截断到 40 字节以内**，别截出半个汉字。
* **必须同时应答单播探测**（不只是广播）。`udp-protocol.md` §11.8 已明确要求这一点：
  将来 A 端要做「定向直发前的在线探测」时会往目标 IP 的 `9001` 单播一次
  `DISCOVER`，B 端如果只处理广播，这个探测就会失败。
  （实现上无需区分：`recvfrom` 收到的无论是广播还是单播，都按同一套逻辑回。）

> **绝对不要做的事**：不要转发报文、不要对非法报文回错误包。否则局域网里容易
> 形成广播风暴。校验不过就丢弃。

### 3.3 Android 上最容易翻车的三条（真机血泪）

A 端已经在同一套环境里踩过这些坑，B 端会一模一样地踩一遍：

**(1) 必须持有 `MulticastLock`，否则收不到广播**

Android 的 WiFi 驱动在省电状态下**直接丢弃广播/组播帧**（只保证单播）。所以：

```xml
<uses-permission android:name="android.permission.CHANGE_WIFI_MULTICAST_STATE"/>
```

```kotlin
val wifi = applicationContext.getSystemService(Context.WIFI_SERVICE) as WifiManager
val lock = wifi.createMulticastLock("eeg-receiver").apply { setReferenceCounted(false) }
lock.acquire()            // 必须在开始监听 9001 之前
// ... 收包循环 ...
lock.release()            // 退出时
```

**不持锁的现象是「A 端一直提示未发现接收端，且抓包一个包都看不到」** ——
非常容易被误判成「网络不通」或「防火墙拦了」，实际是内核静默丢弃。

建议同时再持一个 `WifiLock(WIFI_MODE_FULL_HIGH_PERF)`，避免 WiFi 进省电模式
导致数据流丢包。

**(2) 接收端要长时间驻留 → 用前台服务**

Android 8+ 会冻结普通后台进程。息屏几分钟后接收端会**悄悄停止收包**，而界面
上看不出来。必须用 `startForeground()` 承载监听循环，并在通知栏持续显示状态。

**(3) USB 调试与真机安装的注意事项**

* 两台手机都连在同一个热点上（A 开热点，B 连上）。
* 部分路由器/热点开启「客户端隔离」时，两台设备之间**无法互发广播**，
  自动发现会失效。此时改用填 IP 直发（A 端用 B 的地址）。
* Android 16+ 访问局域网需要 `ACCESS_LOCAL_NETWORK` 权限，且 `targetSdk` 抬高
  会触发强制门槛。B 端若也要主动发广播（例如给 C 端发指令），建议同样声明
  `ACCESS_LOCAL_NETWORK`，并把 `targetSdk` 控制在 35（与 A 端一致）。

### 3.4 数据流解析

按 `udp-protocol.md` §2–§5 实现即可，`§8` 已给出一份可跑的 Python 参考解析器。
B 端需要额外做的只有两件事：

1. **保留 `sampleRate` / `channelCount` / `channelNames`**（来自 `STREAM_INFO`），
   后续所有数组尺寸都从这里推，不要写死 62 / 1000。
2. **不要依赖 `STREAM_STOP`**：当前 A 端推满 4 秒就**静默闲置**，不发收尾报文。
   你必须用**静默超时**（建议 ≥200 ms 收不到 `SAMPLE_BLOCK`）判定一次想象结束。
   下一次按键是**全新一路流**（`seq` 从 1 重来、`firstSampleIndex` 从 0 重来），
   不能把两路流的数据拼在同一个窗口里。
   若是日后 A 端启用了 `STREAM_STOP`（`reason=0x01`），收到时也要能同样清窗。

### 3.5 通道选择：**按名字定位，别按位置**

**推荐只用 9 个枕顶通道做 CCA**，这是实测口径：枕区是 SSVEP 最强的地方，
用全部 62 通道反而会把肌电、眼电、额区噪声拉进来。

| 通道名 | 下标（62 通道协议顺序） |
|--------|------------------------|
| `Pz` | 24 |
| `O1` | 28 |
| `Oz` | 29 |
| `O2` | 30 |
| `P1` | 41 |
| `P2` | 42 |
| `POz` | 43 |
| `PO3` | 60 |
| `PO4` | 61 |

排序后：`[24, 28, 29, 30, 41, 42, 43, 60, 61]`

> **⚠️ 本数据集里没有 `PO7` / `PO8`。**
> 常见 SSVEP 论文的 11 通道清单是 `POz/PO3/PO4/Oz/O1/O2/Pz/P1/P2/PO7/PO8`，
> 但 OpenBMI 这套 62 通道布局里**不存在 PO7、PO8**（见 `udp-protocol.md` §3
> 的通道表）。照抄 11 通道清单会在取通道时失败或取到错通道。
> 本手册所有实测数字都是**这 9 个通道**的结果。

实现上**必须按名字取通道**：

```python
want = ["Pz", "O1", "Oz", "O2", "P1", "P2", "POz", "PO3", "PO4"]
picks = [names.index(c) for c in want if c in names]   # 62 通道布局 -> 9 个
print(len(picks), picks)      # 9 [24, 28, 29, 30, 41, 42, 43, 60, 61]
```

写死下标也能跑，但一旦 A 端将来换成别的布局（例如 64 通道电极帽）就全错位了，
而且错位是**静默的** —— 不会报错，只会判不准。

### 3.6 环形缓冲与丢包

用 `seq`（包头）和 `firstSampleIndex`（块内）**双重**检测丢包：

| 情况 | 处理 |
|------|------|
| `seq` 不连续 | 记录丢包数（用于评估链路质量），不必告警 |
| `firstSampleIndex` 有缺口 | 缺口 ≤ 50 ms（≤10 个采样点）→ **补零**填满，保持时间轴连续 |
| 缺口 > 50 ms | **补零**但重置投票状态（窗口被污染，别基于它做决策） |
| 收到重复 `firstSampleIndex` | 丢弃该包 |

**为什么优先补零而不是跳过**：CCA 的参考信号严格按 `采样序号 × (1/fs)` 对齐时间。
跳过样本会让窗口内的时间轴压缩，等价于把 12 Hz 看成 12.1 Hz，相关系数会掉。
补零代价是窗口里多了一段静音，只影响那一个窗口。

缓冲长度建议 ≥ 30 s（62 × 30000 × 4 ≈ 7.4 MB，可接受），方便事后回溯排错。

### 3.7 时间戳怎么用

`deviceTimeUs` 与 `firstSampleIndex` 严格线性（`udp-protocol.md` §4），所以：

* **做窗口对齐时用 `firstSampleIndex` 就够了**，不需要 `deviceTimeUs`。
* `deviceTimeUs` 的用途是**记录本机处理延迟**（收到时刻 − 设备时间戳 = 网络+排队
  延迟），排查卡顿时有用。**不要**用它做分类窗对齐（它的时钟来自 A 端，与本机
  时钟没有共同时基）。

## 4. 信号预处理

### 4.1 带通要在**连续流**上做（并记住：换滤波器就要重标阈值）

**要求：先把连续流带通好并写入缓冲，再从已滤波的缓冲里切窗。**

```
❌ 不要：raw[win] → 带通 → CCA       （每个窗各自起滤，滤波器状态不连续）
✅ 正确：raw[流] → 带通 → 环形缓冲 → 取 win → CCA
```

对**流式 IIR** 来说这是硬要求：滤波器状态必须跨包保留（§4.2 方案 A）。
每个窗都从零状态重新起滤，窗首会有一段瞬态。

> **实测澄清（重要，早期草稿的结论已作废）**
>
> 早期草稿写「对每个窗单独带通会让相关系数**虚高 10 个百分点以上**」。
> 用 `tools/acceptance_probe.py --live-sim` 实测（4 s 窗，同一套 CCA 与门控，
> 只改带通缓冲口径）：
>
> | 口径 | 方向 ρ 均值 |
> |------|-----------|
> | `pad=0`（每窗单独带通） | 0.6413 |
> | `pad=1500`（连续流带通后切窗） | 0.6455 |
>
> 差 **−0.0042**：每窗单独带通在本数据上**并没有**让 ρ 虚高。原因是本机参考
> 实现用的是**循环** FFT 滤波（`degrade_reference.py` 的 `circular_filter()`），
> 循环卷积按构造不存在边界，「边缘振铃」这个机制在该实现里不会发生。
> 补测非循环口径也一样：补零 FFT 掩码 −0.0010、2 级 IIR +0.033、3 级 IIR
> +0.055、`filtfilt` 风格双向 IIR +0.067 —— 最大也只有 6.7 个百分点。
>
> **但真正的问题比原来说法更严重**：ρ 对**带通实现的陡度**很敏感，滤波器越陡，
> **静息段**的最高分被抬得越高，直到越过 `θ₁`：
>
> | 带通实现（4 s 窗） | 方向 ρ | 静息最高 | `θ₁=0.57` |
> |------------------|-------|---------|----------|
> | 循环 FFT 掩码 4~45 Hz（本机参考口径） | 0.7378 | 0.5324 | ✅ |
> | 逐窗 IIR 2 级（RBJ biquad） | 0.7565 | 0.5685 | ✅（贴边） |
> | 逐窗 IIR 3 级 | 0.7724 | **0.5997** | ❌ **静息被击穿** |
> | 逐窗 `filtfilt` 风格（双向） | 0.7826 | **0.6162** | ❌ **静息被击穿** |
>
> 症状正是「踩着不动也在前进」。所以 §4.1 的结论（要对连续流做、别每窗重起滤）
> 仍然成立，但**理由不是「虚高 10 个百分点」**，而是「ρ 的绝对值随滤波器实现
> 漂移，阈值必须跟着重标」。详见 **§5.6「θ₁ 不可移植」**。

### 4.2 推荐的流式实现

**方案 A（推荐）：IIR 带通 + 状态跨包保持**

用 4 阶 Butterworth 带通（4~45 Hz）拆成 2 个二阶节（SOS），逐样本前向滤波，
二阶节的状态 `zi` 跨包保留，输出连续写入缓冲。

```python
from scipy.signal import butter, sosfilt, sosfilt_zi
sos = butter(4, [4.0, 45.0], btype="bandpass", fs=1000.0, output="sos")
zi = sosfilt_zi(sos) * 0.0            # 每通道一份状态，初始 0

# 每收到一块数据（5 点 × 62 通道），只处理需要的 9 个通道
out, zi_9 = sosfilt(sos, block[:, picks], zi=zi_9, axis=0)
```

优点：O(1) 每样本、无边界振铃、延迟只有滤波器群延迟（几十 ms，可忽略）。

> **⚠️ 这一档恰好贴着阈值。** 实测 4 阶 Butterworth（= 2 个二阶节）下，
> 4 s 窗静息段最高分 = **0.5685**，而 `θ₁=0.57` —— 余量只有 **0.0015**。
> 也就是说：**用推荐实现照抄 `θ₁=0.57`，几乎必然把静息判成方向。**
> 这不是实现 bug，是「阈值不可移植」的直接后果（§5.6）。
> 装好滤波器后第一件事就是在自己的静息段上重标 `θ₁`。

**方案 B（可接受）：频域带通，对整段连续流做**

对一段连续数据（比如最近 30 s）做 FFT → 掩码 4~45 Hz → IFFT，然后从结果里切窗。
等价于 `tools/degrade_reference.py` 里的 `circular_filter()`。精度更高，但要整段
处理，适合离线评估，实时流上偏重。**本手册 §5.3 的基线数字（含 `θ₁=0.57`）
就是这个口径测出来的**，所以照抄时尤其容易踩上面的坑。

**方案 C（不推荐）：对每个窗口单独带通。**

数值上它**未必**虚高（实测仅 +0.004，§4.1）。但它的滤波器状态每个窗都从零起，
瞬态长度随实现变化，`ρ` 会随实现漂移，而且没有任何好处。**统一用方案 A。**

> 如果你用 Python + scipy，注意 `filtfilt` 需要**整段数据**（它会前后各跑一遍），
> 实时流上无法使用。实时必须是 `sosfilt`（单向前向，保留状态）。
> 本机 Python 环境没有 scipy，但 B 端是独立项目，用 pip 装即可。

### 4.3 工频与漂移

* **50 Hz 工频**：4~45 Hz 带通已经把 50 Hz 排除在外，**不需要额外陷波器**。
  （这也是选 45 Hz 而不是 50 Hz 作上限的原因。）
* **基线漂移**：带通下界 4 Hz 已经滤掉。若发现缓慢漂移导致相关值波动，可让
  CCA 前再做一次每通道去均值（CCA 内部本来就去均值，一般不需要）。
* **眼电/肌电**：本数据集保留了眼电与肌电（真实录制）。4 s 长窗 + 枕区通道
  已经能容忍偶发眨眼；不建议做 ICA 之类重处理（收益不确定，风险是引入伪迹）。

### 4.4 预处理自检

写完预处理后，先做这两个合成信号测试，能提前发现 90% 的实现错误：

| 测试 | 构造 | 期望 |
|------|------|------|
| 正对照 | `sin(2π·12.00·t)`，1000 Hz，4000 点 | `ρ(12.00)` ≈ **1.0**（>0.95） |
| 负对照 | 纯高斯白噪声，同样长度 | 4 个 `ρ` 都 ≈ 0.1~0.4，且**彼此接近** |

如果正对照的 ρ 只有 0.5~0.8，说明参考信号的时间轴与数据没对齐（最常见原因：
参考信号用 `arange(n)/fs` 而数据错位了，或误用了 `n` 而非实际窗长）。

## 5. 分类：CCA 与 FBCCA

### 5.1 参考信号

对每个候选频率 `f`，构造 `n×6` 的参考矩阵 `Y`（`n` = 窗长 = 4000）：

```
Y[:, 2k-2] = sin(2π · k · f · t)
Y[:, 2k-1] = cos(2π · k · f · t)        t = arange(n) / fs, k = 1,2,3
```

**候选频率（与方向严格对应，写错会把左右判反）：**

| 方向 | 指令值 | 频率 |
|------|--------|------|
| `forward` 前进 | 1 | **12.00 Hz** |
| `left` 左转 | 2 | **8.57 Hz** |
| `right` 右转 | 3 | **6.67 Hz** |
| `backward` 后退 | 4 | **5.45 Hz** |
| `stop` 停 | 0 | 无参考频率（判定方式见 §6） |

> ⚠️ 早期交接文档把 left/right 写反了。实测校正后的组合是
> `forward=12.00, left=8.57, right=6.67, backward=5.45`，
> 两种独立方法（CCA 混淆矩阵 100/100 + 锁相谱谐波一致性）结论一致，
> 证据见 `udp-protocol.md` §7。频率**不进入任何报文**，只在 B 端本地使用。

### 5.2 CCA 的定义与实现

CCA 求两组多变量信号的线性组合，使二者的相关系数最大：

```
ρ(X, Y) = max      corr(X·w_x , Y·w_y)
         w_x,w_y
        = σ₁( (XᵀX)^{-1/2} · XᵀY · (YᵀY)^{-1/2} )
```

`σ₁(·)` 表示最大奇异值。工程上**不要真去算矩阵开方**，用 QR + SVD 即可，
数值上也更稳：

```python
def cca(x, y):
    """x: (n, C) 脑电;  y: (n, 6) 参考信号;  返回最大典型相关系数"""
    x = x - x.mean(axis=0, keepdims=True)
    y = y - y.mean(axis=0, keepdims=True)
    qx, _ = np.linalg.qr(x)        # (n, C) 正交基
    qy, _ = np.linalg.qr(y)        # (n, 6) 正交基
    return float(np.linalg.svd(qx.T @ qy, compute_uv=False)[0])
```

**关键优化**：参考矩阵 `Y` 只与频率和窗长有关，**与数据无关**，所以
`qy = qr(Y)` 可以在启动时算好并缓存（4 个频率 × 1 份，共 4 个 `4000×6` 矩阵，
内存可忽略）。这样每次决策只剩一次 `qr(x)` 和一次小 SVD。

### 5.3 实测基线（9 通道 / 4~45 Hz / 3 次谐波 / 非重叠窗）

数据来源：`tools/degrade_reference.py`，本机对 `sess01_subj01` 全部 18 段
（4 方向 × 4 个真实试次 + 2 段静息）的实测。样本量：**16 个方向窗 + 2 个静息窗**。

| 窗口 | `ρ_true`（正确方向均值） | `ρ_2nd`（第二名均值） | 静息段最高 | 方向段最低 |
|------|------------------------|----------------------|-----------|-----------|
| **4 s** | **0.7361** | 0.3760 | **0.5388** | **0.6018** |
| 2 s | 0.7727 | 0.5392 | 0.7065 | 0.6291 |

* 4 s 窗：4 个候选全都判对（16/16），绝对门区间 `(0.5388, 0.6018)` **宽 +0.0630**。
* 2 s 窗：静息最高 `0.7065` **高于**方向最低 `0.6291` → 区间为负，**无解**。

### 5.4 FBCCA：可以升级，但**阈值必须重标**

FBCCA（滤波器组典型相关分析）比裸 CCA 更准，是 SSVEP 的标准做法。做法：

1. 把信号按子带分解（常用 5 个子带，通带下限 `6/14/22/30/38` Hz，上限取 `90` Hz
   或 Nyquist）；
2. 每个子带 × 每个候选频率各算一次 CCA，得 `ρ_b(f)`；
3. 加权平方和（`Chen et al. 2015` 的权重）：

```
ρ̂(f) = Σ_{b=1}^{Nb}  w(b) · ρ_b(f)²        w(b) = b^(-1.25) + 0.25
```

4. 取 `argmax_f ρ̂(f)`。

**⚠️ 升级后阈值不能沿用 0.57。** FBCCA 的 `ρ̂` 是加权平方和，数值分布与裸 CCA
的 ρ 完全不同（通常明显更高）。沿用旧阈值的结果是「一直判方向、永远不判停」。

**建议路径**：先用裸 CCA 跑通全链路（`θ₁=0.57` 可作**起点**，但必须在自己的
静息段复核，见 §5.6），再用 §9 的降质流程为 FBCCA 重新标定一套阈值。

> 本机的标定脚本目前是裸 CCA。要标 FBCCA 的话，在
> `tools/degrade_reference.py` 的 `score_windows()` 里替换打分函数，
> 然后重新跑一遍即可得到新的 ρ 分布与阈值区间。

### 5.5 常见错误清单

| 症状 | 最可能的原因 |
|------|--------------|
| ρ 普遍偏高（静息也有 0.7+） | 带通太陡（3 级 IIR / `filtfilt` 风格）把静息最高分抬过了 `θ₁`（§4.1/§5.6）；或窗长太短（2 s，§6.1） |
| 滑动窗下静息偶尔被判成方向 | 阈值是按「试次对齐窗 + 本机理想滤波」标的，没在真机静息段重标（§5.6） |
| ρ 普遍偏低（正向测试到不了 0.9） | 参考信号时间轴与数据错位；或窗长/采样率传错 |
| 左右总是判反 | 候选频率表里 left/right 写反（§5.1） |
| 通道取错但不报错 | 按位置取通道而非按名字（§3.5） |
| 第一次决策特别慢 | 每次决策都在重算 `qr(Y)`（应该缓存） |

### 5.6 `θ₁` 不可移植：它的三条前提（实测，务必先读）

`θ₁=0.57` **不是这个任务的性质**，而是一组特定前提下的实测产物。前提一变，
`ρ` 的分布就变；而可用余量总共只有 `0.0630`，**比前提变化带来的偏移小一个量级**。

| 前提 | 违反后的实测偏移 | 后果 |
|------|----------------|------|
| **(1) 4 s 窗** | 2 s 窗静息最高 0.7065 > 方向最低 0.6291 | 区间为负，**无解**（§6.1） |
| **(2) 理想的 4~45 Hz 带通** | 跨实现 ρ 极差 **4.5 个百分点**（4 s窗） | 静息最高被抬过 `θ₁` → **静息判成方向** |
| **(3) 窗与录制试次对齐** | 滑动窗均值 0.6455 vs 对齐窗 0.7353（**−9 个百分点**） | 静息最高升到 `0.5703` → **≥ `θ₁`** |

**（1）带通实现：同一个 `θ₁` 换滤波器就不安全。**
`tools/acceptance_probe.py --filter-check` 实测（4 s 窗，`θ₁=0.57`）：

| 带通实现 | 方向 ρ | 方向最低 | 静息最高 | `θ₁` 安全性 |
|---------|-------|---------|---------|-----------|
| 循环 FFT 掩码 4~45 Hz（参考口径） | 0.7378 | 0.6364 | 0.5324 | ✅ |
| 逐窗 IIR 2 级（RBJ biquad，§4.2 方案 A） | 0.7565 | 0.6235 | 0.5685 | ✅ 余量仅 0.0015 |
| 逐窗 IIR 3 级 | 0.7724 | 0.6480 | **0.5997** | ❌ 静息被击穿 |
| 逐窗 `filtfilt` 风格（双向） | 0.7826 | 0.6725 | **0.6162** | ❌ 静息被击穿 |

2 s 窗重复同一实验：**四种口径全部击穿**（静息最高 0.7146 ~ 0.7672），与 §6.1
的结论一致 —— 窗长是第一位的硬约束。

> 机制：滤波器越陡，静息段的最高 `ρ` 被抬得越高。静息段的 `ρ` 本来就靠偶然
> 相关撑着，对滤波器的谱特性比方向段敏感。**具体成因尚无定论，所以更要实测。**

**（2）窗口对齐：本机标定用的是「试次对齐窗」，比真实滑动窗乐观。**
`--live-sim` 实测：与录制试次对齐的 4 s 窗 ρ 均值 `0.7353`（正好等于 §5.3 的
`0.7361`），但**所有滑动偏移的平均只有 `0.6455`**，低约 9 个百分点。
原因：本项目回放数据由 4 s 试次**拼接**而成，跨试次边界的窗有相位跳变。
后果：滑动窗下静息段最高分 = `0.5703 ~ 0.5724`，**已经 ≥ `θ₁=0.57`**。

> 这是**数据集特性**，真机连续录制不一定有这个问题。但只要你的 B 端用滑动窗
> （§6.3 要求如此），就必须在**真机静息数据**上重新测「静息最高分」，
> 不能照抄 0.57。

**（3）正确做法：把标定固定在你自己的实现上。**

1. **先冻结** B 端的带通实现、窗长、步进，之后不要再改；
2. 受试者「什么都不做」连续 ≥ 30 s，用 B 端**自己的流水线**记录静息 `ρ` 分布；
3. 受试者按方向注视各 4 s 数次，记录方向 `ρ` 分布；
4. `θ₁` 取「静息最高分」与「方向最低分」的**中点**；两者必须**不重叠**，
   且区间宽度 ≥ `0.03` 才有意义；
5. 把这三条前提（滤波器、窗长、步进）和 `θ₁` **写在一起**，随实现一起改。

> 验收工具：`tools/acceptance_probe.py --filter-check` 做跨实现对照，
> `--sweep` / `--degrade <mode> --alpha <a>` 直接给出**逐窗门控判决**
> （判对 / 判停 / 静息判停），用来检查 `θ₁` 在你的数据上是否既不过松也不过紧。

## 6. 决策层：这是「停得住」的关键

### 6.1 「无指令」判定的真相（必须先理解）

SSVEP 的正确表述是：**4 个方向里哪个分量最强**。如果不加约束，那 4 个候选里
**总有一个最大** —— 哪怕受试者闭着眼睛休息。所以必须有拒绝机制，否则轮椅会
「一直朝某个方向走」。

直觉上可以「找一个阈值」。但阈值能不能存在，**取决于窗口长度**：

| 窗口 | 静息段最高 ρ | 方向段最低 ρ | 可用阈值区间 | 结论 |
|------|-------------|-------------|--------------|------|
| 4 s | 0.5388 | 0.6018 | `(0.5388, 0.6018)` 宽 +0.0630 | ✅ 存在 |
| 2 s | 0.7065 | 0.6291 | 负（`-0.0774`） | ❌ **不存在** |

窗口越短，偶然相关越大（2 s 窗里静息段能刷出 0.7065），而方向段的 ρ 只从
0.7361 涨到 0.7727 —— **静息涨得比方向快**，两侧就交叉了。

差值门（`ρ_top1 − ρ_top2`）也一样：4 s 时静息 gap 最大 0.2107 / 方向 gap 最小
0.2783（可行）；2 s 时 0.1817 / 0.0566（倒挂）。

> **结论：窗口 ≥ 4 s 是硬约束，不是调参偏好。** 要压延迟只能靠滑动窗 + 投票
> （§6.3/§6.4），不能靠缩短窗口。

### 6.2 双门控

每个窗算完后，按下面两步判决：

```
ρ = [ρ(12.00), ρ(8.57), ρ(6.67), ρ(5.45)]
top1, top2 = 最大的两个
winner = argmax ρ

if ρ[winner] < θ₁:                # 绝对门：整体太弱，谁都不像
    → 无指令
elif ρ[winner] - ρ[top2] < θ₂:    # 差值门：两个候选咬得太紧，分不出来
    → 无指令
else:
    → 输出 winner 对应的方向
```

| 门 | 4 s 窗取值 | 依据 |
|----|-----------|------|
| `θ₁`（绝对门） | **0.57** | 区间中点 `(0.5388+0.6018)/2 ≈ 0.5703` |
| `θ₂`（差值门） | **0.245** | 区间中点 `(0.2107+0.2783)/2 ≈ 0.2445` |

**建议不要只用一个门**：绝对门负责「信号整体太弱」（走神、疲劳、降质），
差值门负责「两个方向混淆」（用户盯着边界、波及）。两者抓的是不同故障。

> **⚠️ 这两个数只在 §5.6 的三条前提下有效，直接照抄大概率出事。**
> 尤其是 `θ₁=0.57`：用 §4.2 方案 A 的 4 阶 Butterworth，静息最高分就有
> `0.5685`（余量 0.0015）；用 3 级 IIR 或 `filtfilt` 风格更是直接 0.60/0.62，
> 静息必被判成方向。**上线前必须按 §5.6(3) 在自己的静息段上重标。**

### 6.3 滑窗与决策节拍

* 窗长 `4000` 点（4 s），步进 `200` 点（200 ms）→ 相邻窗重叠 95%。
* 每 200 ms 得一组新的 `ρ`，更新一次判决。
* **首次输出需要窗口填满**：从开始注视到第一次出判决约 `2.5 ~ 4 s`。
  这不是实现慢，而是物理约束 —— 数据本来就要攒够。

**演示与验收要求：一次意图必须连续注视 ≥ 4 s（保守 5 s）。**
抓包测试时按 0.9 s 能验证链路，但**看识别效果时必须按够 4 s 以上**。

> A 端每类波形长 16 s 且是**硬回绕**循环（`udp-protocol.md` §10）。所以一直按住
> 会遇到「第 4 个试次回到第 1 个试次」的跳变点。因为跳变两端**是同一个方向**，
> 对分类没有影响，不必特殊处理。静息段只有 8 s，最多支撑 2 个不重叠窗。

### 6.4 多窗投票

单窗判决会有抖动（偶尔一个窗判错）。用一个长度为 3 的滑窗投票：

```
history = deque(maxlen=3)
history.append(current_decision)          # 可能是 0..4
if len(set(history)) == 1:                # 连续 3 个窗完全一致
    stable_decision = history[0]
else:
    stable_decision = None                # 不稳定 → 保持上一次输出（不切换）
```

* 起点建议 `3` 窗（= 400 ms 确认时间）。要求越严格越稳，但反应越慢。
* 投票**只在判决层做**，不要对 ρ 做平均（不同窗的 ρ 含义不同，平均没有物理意义）。

### 6.5 去抖迟滞

即使投票通过，指令切换也要加最小保持时间（建议 300 ms）：

```
if stable_decision != last_sent and now - last_change_time > 300ms:
    send(stable_decision)
    last_change_time = now
```

注意：**「停」和方向之间的切换不加迟滞的方向性差异** —— 从任方向切到「停」
应该**尽快**（安全优先），从「停」切到方向可以稍慢。工程上可以只对
「方向 → 方向」的切换加迟滞，方向 → 停立即生效。

### 6.6 安全超时（兜底，不可省）

两道超时，缺一不可：

| 层 | 条件 | 动作 |
|----|------|------|
| B 端 | 超过 `1 s` 没有产生新判决（例如 A 端断流） | 发「停」 |
| C 端 | 超过 `1 s` 没收到任何 B → C 报文 | 强制「停」并提示链路断开 |

C 端那道是**独立实现**的兜底（Unity 侧），不能因为「B 端已经很可靠了」就省掉 ——
B 端进程被系统杀掉时，超时是唯一还能保护演示的东西。

### 6.7 状态机伪代码

```python
state = "WAITING"          # WAITING / ACTIVE
last_sent, last_change, last_decision_time = 0, 0, now()

def on_window(win):                     # 每 200 ms 调用一次
    global state, last_sent, last_change, last_decision_time
    if state == "WAITING":
        if win.first_sample_index == 0:  # 新的一路流开始
            votes.clear()
        state = "ACTIVE"

    rho = [cca(win.data, qy[f]) for f in CANDIDATE_FREQS]   # 已缓存 qy
    decision = double_gate(rho)          # -> 0..4，或 None(无指令)
    if decision is None:
        decision = 0                     # 门控不过 = 停

    votes.append(decision)
    stable = votes[0] if len(votes) == VOTE_N and len(set(votes)) == 1 else None

    if stable is not None and stable != last_sent:
        if stable == 0 or now() - last_change > HYSTERESIS_MS:
            send_command_to_c(stable)
            last_sent, last_change = stable, now()

    last_decision_time = now()

def watchdog():                          # 独立线程/定时器
    if now() - last_decision_time > 1000: # A 端断流
        if last_sent != 0:
            send_command_to_c(0)
            last_sent = 0
```

### 6.8 个体标定流程（真人使用前必做）

离线阈值 `0.57` 是特定被试的结果。换人使用前按这个流程重标：

1. **静息标定**：受试者闭眼放松、不作任何注视，采集 **60 s**。
   按 4 s 滑窗统计 `ρ` 的分布，取**最高值**作为 `θ₁` 的下界候选。
2. **方向标定**：4 个方向各注视 **30 s**，统计每个方向 `ρ_true` 的**最低值**
   与 `ρ_second` 的最高值。
3. 取 `θ₁` 落在 `(静息最高, 各方向最低)` 区间内（取中点最稳）。
4. 用 §9 的降质流程验证阈值行为：把 ρ 压到 θ 以下，确认判「停」而不是判错方向。
5. 把标定结果写进配置，**不要写死在代码里**。

## 7. 输出：B → C 指令

### 7.1 报文格式

完整定义见 `system-architecture.md` §4.1（草案 v1）。要点：

| 项 | 取值 |
|----|------|
| 端口 | `9100` |
| magic | `0x47F0`（线上字节 `F0 47`） |
| 报文长度 | 固定 **24 字节** |
| `command` | `0`停 `1`前进 `2`左转 `3`右转 `4`后退 |
| `confidence` | float32，**原始 CCA 获胜相关值**（§7.4） |
| `windowMs` | 本次决策所用窗长（本项目 `4000`） |
| `flags` | bit0 = `confidence` 有效，其余 0 |
| `crc32` | 对 `[0, 20)` 计算 |

### 7.2 发送策略：降频重复，不是「变了才发」

* 指令**变化** → 立即发一包；
* 指令**没变** → 降频到 **2 Hz** 继续发同一指令。

这样 C 端只需要一套逻辑（记住最近收到的指令），不用区分心跳包和指令包，
也不怕丢一个包就永久停在旧状态。

### 7.3 B 怎么找到 C（推荐方案：C 端广播信标）

见 `system-architecture.md` §4.4。推荐让 C 端每秒广播一包 `msgType=0x02`，
B 端收到即学到 C 的 `address:port`，超过 3 s 没收到视为 C 下线。

理由：C 的 DHCP 地址每次重连会变，手工填 IP 是演示现场最容易翻车的环节；
而让 Unity 每隔 1 秒广播一次，比让 Unity 实现完整的 CRC32 应答协议省事得多。

### 7.4 `confidence` 字段的语义（重要）

`confidence` = **本次决策的 CCA 获胜相关值 `ρ`**，范围约 0.2 ~ 0.9。

* 它是**原始相关值**，不是概率，也**不是「专注度」**（§1.3）。
* 应用层要用它做「多可信」的提示时，直接显示 ρ 即可，但阈值判断仍应使用
  §6.2 的双门控结果，不要把 ρ 换算成百分比来当概率解释。
* 4 s 窗下的参考量级：方向合法判决约 `0.60 ~ 0.85`；静息约 `0.35 ~ 0.54`；
  降质到地板时约 `0.30`。

### 8.1 权限与清单

```xml
<uses-permission android:name="android.permission.INTERNET"/>
<uses-permission android:name="android.permission.ACCESS_NETWORK_STATE"/>
<uses-permission android:name="android.permission.ACCESS_WIFI_STATE"/>
<uses-permission android:name="android.permission.CHANGE_WIFI_MULTICAST_STATE"/>
<uses-permission android:name="android.permission.ACCESS_LOCAL_NETWORK"/>
<uses-permission android:name="android.permission.NEARBY_WIFI_DEVICES"
                 android:usesPermissionFlags="neverForLocation"/>
<uses-permission android:name="android.permission.FOREGROUND_SERVICE"/>
```

`targetSdk` 建议 **35**（与 A 端一致）：抬高会触发 Android 16+ 的局域网访问
强制门槛，而本项目全程只用局域网 UDP，抬高没有任何收益。

### 8.2 线程模型

| 线程 | 职责 | 注意 |
|------|------|------|
| 发现线程 | `recvfrom(9001)` + 回 `ANNOUNCE` | 必须包 `try/except` 后 `continue`（Windows/部分 ROM 会抛假异常） |
| 收包线程 | `recvfrom(9000)` → 校验 → 写环形缓冲 | 单线程串行处理，别在收包线程里做 FFT |
| 带通线程 | 从缓冲取新数据 → IIR 滤波 → 写已滤波缓冲 | 或与收包线程合并（成本很低） |
| 决策线程 | 每 200 ms 取窗 → CCA → 判决 → 发指令 | **用定时器驱动，不要用「每个包触发一次」** |
| 看门狗 | 1 s 无判决 → 发停 | 独立于决策线程 |

**不要在收包线程里做滤波和 CCA**：200 包/秒的节奏被打乱会成片丢包。
**不要用「收够 5 个包就判一次」**当作决策节拍 —— 包到达时刻有抖动，会导致窗口
长度不稳定；用固定 200 ms 定时器 + 从缓冲取最近 4000 点。

### 8.3 性能预算（结论：完全不是瓶颈）

4 s 窗、9 通道、每 200 ms 一次决策：

| 环节 | 单次成本 | 说明 |
|------|---------|------|
| 带通（IIR 2 阶节 × 9 通道） | ~2000 点 × 9 × 5 乘加 ≈ 0.09 MFLOP | 摊到 200 ms |
| `qr(X)`，4000×9 | ≈ 0.65 MFLOP | 主导项 |
| `qr(Y)`，4000×6 | 0（**启动时缓存**） | 见 §5.2 |
| SVD 9×6 | 可忽略 | — |
| 4 个候选合计 | ≈ 2.8 MFLOP | — |

合计约 `14 MFLOP/s`。现代手机 CPU 单核 10+ GFLOP/s，占用 **< 1%**。

**结论：纯 Kotlin/Java 实现足够，不需要 NDK、不需要 GPU、不需要预生成特征库。**
如果实机发现卡顿，先怀疑「在错误的线程里做了重复计算」，而不是「算力不够」。

### 8.4 UI 建议

演示时建议至少显示：**连接状态**（收到多少包 / 丢包率）、**当前 4 个 ρ 值**、
**当前判决**、**一个手动急停按钮**。手动急停是演示安全阀 —— 算法判错时能立刻接管。

## 9. 用 A 端的「人为降质」滑块标定与验收

这是本项目特有的一条**标定捷径**：A 端界面上有两个滑块，能在信号层压低
B 端算出的 ρ，报文格式不变、B 端感知不到（见 `system-architecture.md` §7.5）。
作用是把「受试者走神 / 疲劳」这种**不可控状态**变成**可调旋钮**，用来验证
阈值选得对不对。

### 9.1 两个滑块的差别（决定了它们各自的用途）

| 滑块 | 做法 | 对 ρ 的影响 | 用途 |
|------|------|------------|------|
| **SSVEP 削弱（陷波）** | 把 4 个刺激频率的 1/2/3 次谐波谱线乘 `(1−α)` | `ρ_true` 陡降，**方向仍全部判对**（实测 16/16 一直保持到 α=0.9） | **标定绝对门 `θ₁`** |
| **信号干扰（噪声）** | `x' = x + α·rms·N(0,1)` | `ρ_true` 与静息 ρ **同步下降**；α≥3.5 才开始判错方向 | **测拒识安全性**（信号差时会不会乱下指令） |

两个滑块都是 **100% = 不处理**，往下拖才是降质。

> **先分清两个不同的指标**（本节最容易看错的地方）：
>
> * **「判对」= argmax 命中率**：4 个候选里谁最大，跟门控无关。降质下它一直
>   保持 16/16，直到信号被压得很低。
> * **「门控判决」= 实际输出**：过 `θ₁`/`θ₂` 后才算数。它**比 argmax 更早衰退**，
>   因为窗与窗之间 `ρ` 有抖动，平均值达标不代表每个窗都达标。
>
> **验收要看的是「门控判决」列**，不是「判对」列。两列都由
> `tools/acceptance_probe.py --degrade <mode> --alpha <a>` 直接给出。

### 9.2 两种模式的实测对照表（4 s 窗，本机 `tools/degrade_reference.py`）

**门控判决 = 实测的逐窗输出**，16 方向窗 + 2 静息窗）：

| 0.40 | 16/16 | 0.6334 | 0.4446 / 0.4891 | 方向 **13/16**，静息判停 2/2 | 多数判方向，零星判停 |
| 0.50 | 16/16 | 0.5854 | 0.4039 / 0.4420 | 方向 **9/16**，静息判停 2/2 | **半数**判方向、半数判停 |

> **全程「判错方向」= 0**（两个滑块、从 100% 拖到 0% 的所有 α 档位都是 0），
> 且**静息判停恒为 2/2**。这是本项目最重要的安全结论：降质只会让系统
> 「判停」，不会让它「走错方向」。

### 9.3 从对照表读出的三条结论（反直觉，但很重要）

**(1) 加噪会让绝对门**更容易**选，不是更难。**
看「静息最高 / 方向最低」两列：基线是 `0.5388 / 0.6018`（宽 0.0630），
而 α=2.0 时变成 `0.3431 / 0.3964`（宽 0.0533）—— 两个门**同步下移**，
区间宽度基本保持。原因是静息段的 ρ 本来就靠偶然相关撑着，加噪把它按得
更快。所以在噪声条件下，`θ₁` 不需要重新标定也能用。

> ⚠️ 这条**只在带通实现不变的前提下**成立。加噪不改变 ρ 的整体尺度关系，
> 但换滤波器会（§5.6）。先冻结实现，再用这条结论。

**(2) 陷波全程不判错方向** —— 这正是它作为标定工具的资格。
「降低置信度」和「制造错误指令」是两件事：如果只削掉**一个**频率的谱线，
argmax 会跑到别的方向上去，那是「制造错误」，不是「降低置信度」。
本机实现一次性削掉全部 4 个候选频率（含 1/2/3 次谐波），所以方向判断始终成立
（argmax 实测到 α=0.9 仍是 16/16），只有 ρ 在往下掉。

> 注意区分：argmax 一直是 16/16，但**过门控的输出**在 α=0.55 时只剩 6/16、
> α=0.9 时 0/16（§9.2 表）。两者不矛盾 —— 前者说明「赢家没选错」，
> 后者说明「赢家不够自信，被拒绝门挡掉了」。**我们要的正是后者**。

**(3) 差值门在降质下会先失效。**
基线差值门区间 `(0.2107, 0.2783)` 是**不降质**时测的。加噪到 α≥2.5
（`0.0396 / 0.0282`）或陷波到 α≥0.75（`0.1297 / 0.1231`）时，差值区间就倒挂了。
**结论：差值门 `θ₂` 必须用真实静息段标定，不能用降质滑块来验证**；
降质滑块只能验证绝对门 `θ₁`。

### 9.4 验收步骤（照着做）

前置：A 端与 B 端已连通（B 端日志能看到稳定的 200 包/秒）。

| 步骤 | 操作 | 期望 |
|------|------|------|
| 1 | 两个滑块都 100%，点一下「前进」（自动推 4 s） | B 端稳定输出 forward，`ρ` 约 0.70~0.74，`confidence` 与 ρ 一致 |
| 2 | 同上，点一下「停」 | B 端判 0（停）。若判成方向 → **绝对门偏低**，把 `θ₁` 上调 |
| 3 | 陷波拖到 **80%**（α=0.357） | 仍判 forward，但 ρ 掉到 0.65 左右（门控实测 ≈14/16，偶有窗判停属正常） |
| 4 | 陷波拖到 **60%**（α=0.540） | **时判 forward 时判停**（ρ≈0.56，门控实测约半数判方向）。靠投票压住输出即可，**不要求 100% 判停** |
| 5 | 陷波拖到 **50%**（α=0.604） | **多数窗判「停」**（ρ≈0.52，门控实测约 3/16 仍判方向）。若此时仍稳定输出 forward → `θ₁` 偏高 |
| 6 | 陷波拖到 **0%**（α=0.820） | 稳定判「停」，且**不应出现任何方向输出**（门控实测 0/16）。（若出现方向 → 你的谱线掩码没覆盖全部 4 个频率） |
| 7 | 噪声拖到 **60%**（α=1.545） | ρ≈0.56 → **约一半窗判「停」**（门控实测 7/16 判方向、9/16 判停） |
| 8 | 噪声拖到 **30%**（α=3.787） | ρ≈0.43 → 判「停」（门控实测约 1/16）。此时偶发方向误判属正常（§9.2 表） |
| 9 | 噪声拖到 **0%**（α=8.0） | ρ 触地板约 0.34 → 判「停」（门控实测 0/16）。注意 **0~20% 段是死区**（α 已饱和在 8.0），现象与 20% 相同 |

**第 4、5、6 步是核心**：它们同时验证了「阈值选得对」和「降质工具生效」。
第 6 步还额外验证了你的 B 端不会因为信号劣化而**乱下指令**。

> **判读要点**：降质过程中「判对/判停」的比例是**连续过渡**的，不存在一个
> 「一刀切」的档位 —— 这是 `ρ` 有窗间抖动的必然结果，不是实现有问题。
> 判断 `θ₁` 是否合适，看的是**过渡区间落在哪个滑块位置上**：太靠右（100% 附近
> 就开始判停）说明 `θ₁` 偏高，太靠左（拖到 40% 还在稳定输出方向）说明偏低。
> 另外**先确认自己没有「判错方向」**（全程应为 0）—— 那才是真故障。

> 说明：滑块百分比 → α 的映射由 A 端按 4 s 窗实测曲线标定（`α = f(ρ目标)`，
> 见 A 端 `SignalDegrade.noiseAlphaFor()` / `notchAlphaFor()`）。
> 上表里的 α 是标定出的档位值，与滑块位置的对应关系不是线性的。
>
> **注意**：本表 100% 行的「目标 ρ」= 0.736，是**本机理想滤波器**（循环 FFT
> 掩码）下的值。若 B 端的滤波器更陡，同一档位的实际 ρ 会更高（§5.6），
> 于是「该判停的档位」会整体右移。**对照日志时先记住自己那一档的基线 ρ。**

## 10. 评估方法（怎么写进报告）

不要只报「准确率」。SSVEP 这种带拒识的系统，必须报下面这组指标：

### 10.1 混淆矩阵与准确率

5 × 5 矩阵（4 方向 + 停）。**注意要分开报**「方向间混淆」与「方向↔停」——
后者是拒识能力，前者是分辨率。

### 10.2 准确率–覆盖率曲线（最关键）

* **覆盖率** = 判决为「方向」的窗口比例（其余判「停」）。
* **准确率** = 在判出方向的窗口里，判对的比例。

阈值调高 → 覆盖率 ↓、准确率 ↑。演示要的是「不乱动」，所以应该选**准确率高、
覆盖率可接受**的工作点（例如准确率 ≥ 95% 时覆盖率还有多少）。

只报准确率而不报覆盖率，等于隐藏了「它其实大部分时间都在判停」这一事实。

### 10.3 ROC / AUC

把「方向 vs 静息」当二分类，扫 `θ₁` 画 ROC、报 AUC。AUC 是阈值无关的
可分性度量，适合跨被试比较。

### 10.4 可靠性图与 ECE

把窗口按 `confidence` 分桶（如 0.5~0.6、0.6~0.7…），统计每桶的实际准确率，
画成可靠性图；ECE（期望校准误差）是各桶偏差的加权平均。

意义：`confidence=0.7` 的窗口里，真有约 70% 是判对的吗？如果实际只有 50%，
说明 `ρ` 不是概率、不能直接当概率用（这正是 §7.4 强调「不要换算成百分比」的原因）。
本项目当前**未做**校准，若报告里要用「置信度」这个词，必须说明它只是原始 ρ。

### 10.5 ITR（信息传输率，标志性指标）

```
ITR = [ log₂N + P·log₂P + (1−P)·log₂((1−P)/(N−1)) ] × 60 / T     (bits/min)
```

* `N` = 选项数（本项目方向类 `N=4`，若把「停」算进去则 `N=5`）
* `P` = 准确率
* `T` = 完成一次选择所需时间（秒，含窗口填充 + 投票 + 去抖）

本项目算例（`T` 取 4.0 s、`N=4`）：

| 准确率 `P` | ITR | 备注 |
|-----------|-----|------|
| 1.00 | 30.0 bits/min | 离线理想上限（16/16 窗判对） |
| 0.95 | 24.5 bits/min | 实际可争取的水平 |
| 0.90 | 20.6 bits/min |  |
| 0.80 | 14.4 bits/min |  |
| 0.70 | 9.7 bits/min |  |
| 0.60 | 5.9 bits/min | 已接近不可用 |

注意 ITR 对准确率极其敏感：`P` 从 1.0 掉到 0.7，ITR 掉到不足三分之一。
这就是为什么 §6.4/§6.5 的投票与去抖值得做 —— 它们提升的是 `P`。

## 11. 实现顺序（建议里程碑）

| 阶段 | 目标 | 完成判据 |
|------|------|----------|
| **M1 收包** | 解析 A 端数据流，打印 `sampleRate` / 通道名 / 包速率 | 稳定 200 包/秒，丢包率 < 0.1% |
| **M2 发现** | 实现 `9001` 应答（含 `MulticastLock`） | A 端 IP 留空能自动发现并开始推流 |
| **M3 预处理** | 流式带通 + 合成信号自检（§4.4） | `sin(12 Hz)` 的 ρ > 0.95，白噪声 ρ < 0.5 |
| **M4 CCA** | 4 个候选频率的 ρ，打印到界面 | 点一下「前进」时 ρ(12.00) 明显最高 |
| **M5 判决** | 双门控 + 投票 + 去抖 + 看门狗 | 按 §9.4 步骤 1~6 全部符合期望 |
| **M6 输出** | B → C 指令 + 心跳；先用手写 UDP 脚本当 C 端替身 | 抓包看到 9100 上的 24 字节报文 |
| **M7 联调** | 与 Unity 轮椅模型联调 | 点一下 → 轮椅开始动作；流停止 1 s 内停 |
| **M8 标定** | 真人/多被试标定 `θ₁`、`θ₂`、投票窗数 | 报出 §10 的完整指标 |

每个阶段都能独立验证，**不要在 M3 之前动 CCA**（会分不清是滤波错还是算法错）。

## 13. 已知限制与风险（写报告时要老实写）

| 限制 | 说明 | 缓解 |
|------|------|------|
| **数据是回放，不是实时采集** | A 端播的是 OpenBMI 真实录制波形，判对是因为播的就是对应方向 | 报告与答辩必须如实说明（`system-architecture.md` §7.3） |
| **单一被试** | 全部波形来自 `sess01_subj01` | 跨被试验证需另抽数据；演示时说明 |
| **样本量小** | 阈值统计只有 16 个方向窗 + 2 个静息窗 | 把阈值当**起点**，真人使用前按 §6.8 重标 |
| **延迟较长（≥4 s）** | 4 s 窗口是拒识能力的硬约束 | 用滑动窗 + 投票优化，但不能缩短窗 |
| **低响应者可能用不了** | 约 10%~30% 人群 SSVEP 响应弱（文献值） | 现场先用降质滑块演示阈值行为，说明个体差异 |
| **阈值绑定带通实现** | `θ₁=0.57` 只在「4 s 窗 + 理想滤波器 + 试次对齐窗」下成立；换实现或换滑动窗，ρ 漂移 **4~9 个百分点**，而可用余量只有 0.063 | 上线前按 §5.6 在真机静息段重标；`--filter-check` 可查阈值是否跨实现安全 |
| **不会读心** | 只能从 5 个固定选项里选 | 产品定位是「辅助操作手段」，不是通用操控 |
| **约 10% 窗口会抖动** | 加噪 α=3.5 起出现偶发误判；真人会更明显 | 投票 + 去抖 + 超时 + 急停四道防线 |

### 14.2 公式速查

```
CCA:      ρ = σ₁( (XᵀX)^{-1/2} XᵀY (YᵀY)^{-1/2} )          实现用 QR + SVD
FBCCA:    ρ̂(f) = Σ_b w(b)·ρ_b(f)²,  w(b) = b^(-1.25) + 0.25
判决:     ρ[winner] ≥ θ₁  且  ρ[winner] − ρ[top2] ≥ θ₂
ITR:      (log₂N + P·log₂P + (1−P)·log₂((1−P)/(N−1))) × 60/T
参考信号: Y[:,2k-2]=sin(2πkft), Y[:,2k-1]=cos(2πkft), k=1..3, t=arange(n)/fs
```

### 14.4 一句话总结

> 收 62 通道 @1000 Hz 的流 → 对**连续流**做 4~45 Hz 带通 → 从**已滤波缓冲**里取
> **4 s 窗**里的 **9 个枕顶通道** → 对 4 个候选频率做 **CCA**（参考信号缓存）→
> **双门控 + 3 窗投票 + 300 ms 去抖 + 1 s 超时** → 把 `0..4` 和原始 ρ 发给 9100 端口。
> 窗口不能短于 4 s，带通不能按窗做 —— 这两条错了后面全错；而 `θ₁=0.57` 是
> **本机滤波口径下的起点值，不是通用常数**，上线前必须按 §5.6 重标。
